# Frontend (Svelte 5)

Every component and `src/lib` module, auth (Supabase), styling and the Svelte conventions used here. The project map, rules and directory layout are in `AGENTS.md`, and which `src/lib` modules also run on the server is in `AGENTS.md` → **Where code runs**. Entries are long: search for the file, function or class you need. Moved here from `AGENTS.md` on 2026-11-05.

## Entry and root

- `index.html` loads `/src/main.js` and includes the Google Analytics tag immediately after `<head>`: `gtag.js` loads for `G-5VERECD6ZJ` and the bootstrap configures two GA4 properties, `gtag('config', 'G-5VERECD6ZJ')` then `gtag('config', 'G-6370Y1Y7YS')` (added 2026-11-05), so every page view and event reaches both. Before the `config` calls the bootstrap sends `gtag('set', { traffic_type: 'internal' })` when `localStorage` `arl-ga-internal` is `'1'` (set by `src/lib/analytics.js`; keep the key in sync). After `<div id="app"></div>` sits the **boot card**: a sibling `<div class="boot" role="status">` with sleeping Kimchi (`/content/kimchi-sleep.jpg`, which Vite inlines as a `data:` URI because Express doesn't serve `/content`), three Mint hopping dots and visible text under them, `Waking up…` (`.boot__text--en`) or `On se réveille…` (`.boot__text--fr`), in the system font stack (Inter isn't loaded yet). CSS alone shows the one that matches `<html lang>` (`:lang(fr)`), which the server sets per request (`resolveRequestLocale` in `src/lib/seo-server.js`: `?lang`, then `Accept-Language`); the text is static HTML, not in the locale files. It is invisible for 450ms, then appears in one step (`boot-in 0s 450ms forwards`, no fade), so warm loads never see it; `#app:not(:empty) + .boot { display: none }` hides it the frame Svelte mounts, so `main.js` needs no change. Its CSS is a small inline `<style>` in `<head>` (hex values only), the one deliberate exception to "all CSS in `app.css`": the card must be styled before the bundle's CSS exists, also in dev. It adds no script, so the CSP script hashes are unchanged.
- `main.js` uses Svelte 5 `mount()` when `#app` exists and imports global `app.css`.
- `App.svelte` holds top-level state: `items`, `loading`, `loadError`. It loads inventory on mount (also on the homepage, so the first category click is instant), routes between the homepage (`/`, `HomePage`, imported eagerly because it is the main landing page; `/join` renders it too, with the Register pop-up opened by `HeaderAuth`), inventory (`/equipment`, `/books`, `/rooms`, `/expertise`), **How it works** (`/howthisworks`), **About** (`/about`), **Privacy** (`/privacy`), **Account** (`/account`), and admin (`/admin`) via `src/lib/router.js`. On item routes (`/{tag}/{slug}` e.g. `/equipment/megaphone` or `/expertise/some-expert`) it renders the inventory grid **and** the lazy-loaded `ItemDetailPage` overlay concurrently (the grid stays mounted underneath; `InventoryPanel` filters to the item's tag), so deep links show the item overlay on top of the right category grid. Any other path (`!isKnownAppPath`) renders a small **not-found view** (`not_found.*`: heading, one sentence, link back to the library) in `<main id="main-content">`. It wires a skip link (`site.skip_to_content` → `#main-content`), client-side SEO tags via `src/lib/seo.js` (`$effect` on route + locale; per-item Product JSON-LD on detail routes; on the item URL the page was loaded at it leaves the server-injected tags alone until `ItemDetailPage` reports the item, and after a load error, while a client-side navigation to an item gets the route defaults until the item arrives; item results only count for the path they were loaded for (`itemDetailSeoPath`), since the overlay mounts asynchronously and a slow fetch can finish after the route moved on; a missing item or unknown path gets `getNotFoundSeoConfig` — "Page not found" title + `noindex, nofollow`, no JSON-LD), Google Analytics (`trackGtagPageview`: a `config` with `page_path` for each of the two GA4 ids) + optional Plausible SPA pageviews on route change when each script is present (plus `tagStaffTraffic()` from `src/lib/analytics.js` on mount), a lemon **PSA banner** (localized hyperlink above the header), the site header (logo, which goes home in-app through `goHome` → `navigateToPage('/')` instead of a full reload; `SiteNav`; `LocaleSwitcher`; `HeaderAuth`), lazy-loaded admin / how-it-works / about / privacy / account / item-detail pages, the add-item modal (lazy, mounted only on `/admin`), the site footer (`SiteFooter`, the last child of `.app`, on every page including `/admin` and the not-found view; it carries the FES / AisB credit), and the `KimchiNotification` chat widget. When the route leaves an item path (overlay closed by X, Escape, backdrop, browser Back or a breadcrumb), an `$effect` moves focus to that item's card link (`.inventory-card__title-link`, or a homepage `.home-expert` or `.home-item` link, whose `pathname` is the item path) or, if the card isn't in the grid, to `#main-content h1` (given `tabindex="-1"`). It only acts when focus fell to `<body>`, never on the initial load or other navigation, skips the scroll when the target is already on screen above the bottom `scroll-padding`, and polls briefly (50 ms timer, up to 1 s) for lazy pages such as Back to `/account`. **Lazy chunks across deploys:** each lazy page is a separate content-hashed chunk, and a tab opened before a deploy still asks for the old file names, which the server answers with a plain-text 404. Every lazy `{#await}` has a `{:pending}` branch that renders `RouteProgress.svelte` (the five lazy pages and the item overlay) and a `{:catch}` that renders `PageLoadError.svelte` (`page_load_error.*`, EN/FR): on mount it reloads the page once (skipped when `navigator.onLine === false`; a `sessionStorage` timestamp, `arl-chunk-reload-at`, allows one auto-reload per 60 s so a chunk that stays missing cannot loop), otherwise it shows the message and a **Reload the page** button, in `<main id="main-content">` for pages or floating at the top of the viewport for the item overlay. The `AddItemModal` catch renders nothing (AdminPage's own catch covers `/admin`). There is deliberately no global `vite:preloadError` reload, so a failed background fetch never reloads the page on its own. **Lazy pages without a gap:** the five pages load through `lazyPage(load…)` (`LAZY_PAGES` pairs each route test with its loader), which keeps each module once it has loaded and hands `{#await}` the module itself, so a later visit renders in the same update as the route change instead of passing through `{:pending}` (a fresh `import()` promise always would). `setPageLoader(lazyPageFor)` makes the router wait for a page that hasn't loaded yet, with the current page and its band still up and `RouteProgress` shown while `$pageLoading`; only a cold load of a lazy URL still renders `{:pending}`. A failed import is dropped from the cache, so `{:catch}` (or the next visit) tries again. **Preloading:** a document-level `pointerover` / `focusin` listener (`preloadLinkedPage`) starts loading a lazy page when a same-origin link to it is hovered, touched or focused, so the click usually finds it ready; a failure there is silent. **Item overlay warm-up:** after the inventory loads, `App.svelte` imports `ItemDetailPage` in `requestIdleCallback` (3 s timeout; 1 s `setTimeout` where unsupported), so the first card click opens the overlay without a network round trip and a tab left open across a deploy already holds the chunk; a failed warm-up is silent. The category page header is `site.title` + `site.intro`; the longer welcome copy lives on the homepage. Category paths sync the inventory filter via `navigate(categoryToPath(tag))`. **Item views:** once `ItemDetailPage` reports a loaded item (not a not-found result, and after the stale-path guard), `handleItemDetailLoaded` calls `recordItemView(item.id)` from `src/lib/item-views.js`, which feeds admin **Stats**. **Kimchi from App:** a pending equipment, book or room request sent from the item overlay (`handleReserveSuccess`) arms a pointer to `/account` (`kimchi.track_request_cta` + link `kimchi.track_request_link`), sent with `notifyWhenIdle` about 600 ms after the overlay closes onto any page but `/account`, once per page load and spent only when it shows (C1); a failed inventory load (`loadError`) gets `kimchi.inventory_load_failed` on `/` or a category grid, once per failed load (C5). `HomePage` receives `loadError` too.

## Auth (Supabase)

- **OAuth providers (Google, Discord):** buttons appear automatically for each provider enabled in Supabase → **Authentication** → **Sign In / Providers** (`initAuth` → `loadOAuthProviders()` reads `external.google` / `external.discord` from `/auth/v1/settings`); no env vars or deploy needed. Setup per provider: create an OAuth app (Google Cloud Console → OAuth client, type *Web application*; Discord Developer Portal → OAuth2), set its redirect URI to `https://<project-ref>.supabase.co/auth/v1/callback`, paste the client ID + secret into the Supabase provider. `signInWithOAuthProvider` returns the visitor to the page they started on (`origin + pathname + search`, so `?reserve=1` survives); that URL must match Supabase **Redirect URLs** (add `https://activistresourcelibrary.com/**` and `http://localhost:5173/**`), otherwise Supabase falls back to the Site URL. Supabase links an OAuth identity to an existing account with the same verified email. Discord accounts without a verified email fail at Supabase; the redirect error opens the login modal with `auth.oauth_no_email` (other redirect errors show `auth.oauth_failed` + the Supabase message).
- **Member agreement for OAuth accounts:** OAuth sign-up skips the register form. `userNeedsMemberAgreement(user)` is true when `user_metadata.signed_member_agreement` is not `true` **and** `app_metadata.provider` is not `email` (legacy email accounts that predate the flag are never prompted). If the agreement was signed in the register form before the OAuth click, the choice is stashed in `sessionStorage` (`arl-pending-oauth-signup`, 30 min) and applied with `supabase.auth.updateUser` on return; otherwise `CompleteSignupModal` asks for it. Like the email flow, this is client-side only; the server does not check the flag.
- **Password reset and change** (client-only; Supabase Auth does the work, no Express route):
  - **Request:** login dialog → **Forgot password?** → reset view → `requestPasswordReset(email)` → `supabase.auth.resetPasswordForEmail(email, { redirectTo })`. `redirectTo` is the current page (`window.location` origin + path + query) without `?reserve`, with an item path `/{tag}/{slug}` swapped for its category (the overlay would otherwise open over the new-password dialog), plus `?password_reset=1`. Like OAuth, it must match Supabase **Redirect URLs** — keep `https://activistresourcelibrary.com/**` (and `http://localhost:5173/**`), otherwise Supabase falls back to the Site URL without the flag. The dialog always shows the neutral `auth.reset_sent`, so it never says whether an address has an account; only rate limits, a malformed address and network/server failures show an error.
  - **Landing:** Supabase's verify link redirects to `redirectTo#access_token=…&type=recovery` (implicit flow). supabase-js saves that session and fires `PASSWORD_RECOVERY` on a timer that can run before `initAuth` subscribes, so `supabase.js` notes `type=recovery` synchronously and `passwordPrompt` starts as `'recovery'`; the `PASSWORD_RECOVERY` listener covers late events. supabase-js also relays that event (and the new session) to every other open tab of the site, so the listener only acts when `authCallbackRecovery` is true: the tab where the member asked for the link (often still showing the reset view) signs in but does not open a second dialog. `initAuth` awaits `supabase.auth.initialize()`: if the tokens are rejected it clears the prompt (a stored session, possibly another account, stays signed in and is not offered a new password) and reports `passwordResetLinkFailed`. `SetPasswordModal` then asks for the new password → `updateUser({ password })`. Staff-sent recovery links from the dashboard (no flag) open the same dialog.
  - **Expired or used link:** Supabase redirects with `#error=access_denied&error_code=otp_expired&error_description=…`. With the `password_reset` flag, `HeaderAuth` opens the reset view with `auth.reset_link_expired` (“This reset link has expired or was already used. Request a new one.”) instead of the generic redirect error. Mail scanners that open links ahead of the member can use up the one-time link and cause this.
  - **Change password:** `/account` shows **Change password** only when `userHasPasswordLogin(user)` (an `email` entry in `app_metadata.providers` or `user.identities`); it opens the same dialog in `'change'` mode. If **Secure password change** is on (Supabase → Authentication → Providers → Email), a session older than 24 h gets `reauthentication_needed` → `auth.password_reauth_needed` (log out and back in). Supabase's own minimum length / leaked-password check returns `weak_password` → `auth.password_weak`; keep the dashboard minimum at 8 or lower, or raise `PASSWORD_MIN_LENGTH` and the `auth.password_min_length` / `auth.password_hint` copy with it.
  - **The email:** Supabase sends it, not Resend. Copy is the **Reset Password** template (Authentication → **Email Templates**; one English template per project; it must keep `{{ .ConfirmationURL }}`). Supabase's built-in sender is for testing: it allows only a few emails per hour for the whole project and delivers only to addresses on the Supabase organization's team (others fail with `email_address_not_authorized`, shown as `auth.reset_send_failed`); set **custom SMTP** (Authentication → **SMTP Settings**, e.g. Resend's SMTP with the verified `activistresourcelibrary.com` domain) so reset and confirmation emails arrive. Supabase also rate-limits reset requests per address (about one per minute), which shows as `auth.rate_limited`.
  - **Staff-sent link (admin Members, server route):** **Send password reset** calls `POST /api/admin/users/:id/password-reset`, which makes a one-time recovery link through `auth.admin.generateLink({ type: 'recovery', email, options: { redirectTo } })` with `redirectTo` = `${EMAIL_SITE_ORIGIN}/?password_reset=1` (`EMAIL_SITE_ORIGIN` is `SITE_URL`, else `https://activistresourcelibrary.com`) and emails it through Resend in our branded layout (`docs/automated-emails.md`, trigger 9), so it doesn't depend on Supabase's mailer or SMTP. `generateLink` sends nothing itself, and a new link replaces the account's previous one. The link lands like a member's own reset link: the homepage with **Set a new password**, or `auth.reset_link_expired` once used or expired. The redirect must be allowed in Supabase → **Authentication** → **URL Configuration** → Redirect URLs (`https://activistresourcelibrary.com/**` covers it), otherwise Supabase falls back to the Site URL without the flag. Only for accounts with an email/password login that aren't suspended (400 `password_reset_unavailable`), at most 3 per account per hour.
  - **Stacking:** `CompleteSignupModal` waits while `$passwordPrompt` is set, so a reset link that signs in an OAuth account without the agreement shows the password dialog first, then the agreement.
- Browser client: `@supabase/supabase-js`. **Server:** `requireAuth` middleware validates `Authorization: Bearer <token>` via `getSupabaseAdmin().auth.getUser(token)`; `requireAdmin` requires `@apathyisboring.com` email **and** a confirmed email (`email_confirmed_at` or `confirmed_at` on the Supabase user). **Confirm email MUST stay enabled** in Supabase Auth → Providers → Email so unconfirmed accounts cannot pass `requireAdmin`. Applied to reservation create (auth only) and all inventory admin / reservation mutation routes (auth + admin). `requireAuth` also answers 403 `{ error, code: 'account_suspended' }` for a suspended account (see below).
- **Suspension (admin Members):** **Suspend** sets a GoTrue ban (`auth.admin.updateUserById(id, { ban_duration: '876000h' })`, about 100 years; **Lift suspension** sends `'none'`). Supabase then refuses sign-in and token refresh with `user_banned`, which `AuthModal` (email/password) and `HeaderAuth` (the Google/Discord redirect's `error_code`) show as `auth.account_suspended`. An access token issued before the ban keeps working until it expires (up to an hour), so `requireAuth` also refuses any token whose user has `banned_until` in the future, or that GoTrue reports as `user_banned`; `ERROR_CODE_KEYS` maps the code to `auth.account_suspended` on `/account`. The suspended member's bookings stay as they are. Staff accounts (any `@apathyisboring.com` address, confirmed or not, and the admin's own) can't be suspended or deleted (403 `user_protected`), nor can a mentor (409 `user_is_mentor`). Deleting a member suspends them first, so no request lands mid-way.
- **Display names (admin Members):** staff can give any account a name that only staff see, stored as `user_metadata.display_name` (merged into the existing metadata through `updateUserById`). Google and Discord fill `full_name` / `name`, which they may rewrite on a later sign-in, so it is a key of its own. The Members list shows `display_name`, else `full_name`, `name` or `custom_claims.global_name`, else the email; clearing the name falls back the same way.
- **Email address changes:** the app has no screen for changing an account's email, for members or staff; today it is done in Supabase → **Authentication** → **Users**. The app ties a mentor item (`expert_email`) and reservations (`user_email`) to the address, not the account id, so `014_account_email_change.sql` adds a trigger on `auth.users` that moves those rows to the new address in the same transaction (only when the old address was confirmed). `requireAuth` reads the user from Supabase on every request, so the account sees them under the new address at once. A future in-app change (`supabase.auth.updateUser({ email })` or `auth.admin.updateUserById`) is covered by the same trigger. `015_item_owners_and_reminders.sql` replaces the trigger's function so it also moves `inventory_items.owner_email` (re-run 015 if 014 is applied after it).
- Production loads **`GET /config.js`** before the SPA bundle (`index.html`); Express injects public Supabase URL, anon key, and `SITE_URL` from runtime env. Vite dev proxies `/config.js` to Express; local dev still works via `.env` when the server is not running.
- `vite.config.js` sets `envPrefix: ['VITE_', 'SITE_']` so only `VITE_*` and `SITE_*` keys are exposed to the client build (prevents accidental service-role leak). Supabase public creds come from `/config.js` at runtime or `VITE_SUPABASE_*` in `.env`.
- Enable **Email** provider in the Supabase dashboard. If email confirmation is on, registration shows a “check your email” message and the user logs in after confirming. The page the confirmation link opens (`#type=signup` with a session, `authCallbackSignupConfirmed`) gets Kimchi's `kimchi.email_confirmed` instead of `logged_in`.
- Set **`SITE_URL`** to the public production origin (no trailing slash) for production Docker/Cloud builds so confirmation emails redirect there instead of localhost. Omit locally to use the current browser origin (`http://localhost:5173` in dev). The same URL must be allowed in Supabase → **Authentication** → **URL Configuration** (Site URL and Redirect URLs).
- Header auth UI is omitted entirely when URL or anon key env vars are unset. Admin controls are omitted when auth is unset, the user is signed out, or `isApathyAdmin(session)` is false.

## Styling

- Global CSS in `src/app.css` (not per-component styles). Exceptions: the existing `<style>` blocks in `KimchiNotification` / `KimchiBubble`, the boot card's inline `<style>` in `index.html` (it must render before the bundle's CSS), and Leaflet's own `leaflet/dist/leaflet.css`, added as a `<link>` by `LocationMapPanel` the first time a map opens, so only pages that open a map load it. It arrives after `app.css`, so the map overrides in `app.css` (`.location-map …`) are one class deeper than Leaflet's rules; `.location-map__canvas` has `isolation: isolate` to keep Leaflet's z-index 400–1000 panes under Kimchi.
- **Page layout** (since 2026-10-08; no floating page card). Every page is `<main id="main-content" class="container {name}-page">`, a plain 64rem column on the `Light` page surface (no background, border, radius, shadow or padding) that the site footer lines up with. Its first child is `<header class="page-header">`, a **title band**: a full-width colour block painted with `border-image: linear-gradient(var(--band) 0 0) fill 0 / / 0 100vmax` (the 100vmax side extensions are ink overflow, so no sideways scroll; `.app-body` also has `overflow-x: clip` as a guard). Band colours are custom properties on `.container` (`--band`, `--band-ink`, `--band-link`, `--band-bone`), set per page class: Lemon (homepage, inventory), Lavender (`.how-this-works-page`, `.privacy-page`), Mint with Light text (`.about-page`), Pear (`.account-page`), Dark with Light text (`.admin-page`), Plum with Light text (`.not-found-page`); on the three dark bands links are Lemon. Every band has the same order and spacing, so titles sit at the same height on every page: the Ringold `<h1>` (2.5rem, 2rem on phones, line-height 1.05, `text-wrap: balance`, no margin), one intro line 0.75rem below it (`.page-intro`, `.subtitle` or `.account-page__email`, all 1.0625rem / 1.5 at most 42rem wide in the band's text colour; the homepage adds `home.free` 0.5rem below), any `.page-header__actions`, then the back link last (`.page-header__back` / `.page-header__back-link`, 1.25rem below, `← …`). The homepage and inventory bands have no back link; the 404's is `← Back to the library`. `/account` and `/admin` always render the band: inside it, the auth-gate skeleton (bones tinted by `--band-bone`), the not-configured / sign-in-required / access-denied message with `.page-header__actions` (Log in, Register), or the real heading; the page body below renders only once signed in (and an admin, on `/admin`). Long text keeps a 44rem measure (`.about-section`, How it works steps and FAQ, `.privacy-content`); the `/account` agenda stays at 48rem. Inside pages, cards are one level only and flat: tiles (`.home-category`, `.home-item__frame`, `.inventory-card`) are white with a `--color-border-strong` edge and no shadow at rest; hover lifts them 2px onto a soft shadow (`0 6px 20px var(--color-shadow-strong)`) and leaves the edge as it is; boxes that only grouped text became ruled lists (How it works steps under a 2px `Dark` rule, FAQ items between hairlines, About partners with a 4px left rule in Lemon / Lavender); forms that need an edge (`.about-contact-form`, `.account-share-expertise`, `.inventory-filter`) are white with a `--color-border-strong` border. Dialogs and overlays (`.modal`, the item overlay, `.page-load-error--overlay`) keep their card look and shadow, except the expert overlay, which is flat under design F (below). `PageLoadError`'s page version has no band and keeps 2.25rem above it. **Page changes morph the band** (since 2026-10-08; only its colour and size since 2026-10-09): `.page-header` has `view-transition-name: page-band`, so in a page-to-page view transition (router.js `morphPage`) its group moves and resizes from the old band to the new one over 280 ms (`::view-transition-group(*)`, `--ease-morph`). Nothing else animates: the old root snapshot is `display: none` and the new one has `animation: none`, so the rest of the page switches at once. Inside `@supports (view-transition-name: match-element)` each direct child of the band gets its own snapshot (`view-transition-class: band-text`), which keeps the words painted above the band's group; the old words are `display: none` and the new ones have `animation: none`, so they switch at once too. While the band morphs (`:root.band-morph`, set by router.js) the bands' own snapshots are hidden and `::view-transition-image-pair(page-band)` paints the band, widened to the window (`inset: 0 -100vmax`) and animated from `--band-morph-from` to `--band-morph-to` (`@keyframes arl-band-morph`), so it is one block of colour that resizes and changes colour. Safari flickered when the band was drawn from its snapshots (their 100vmax `border-image` sides are ink overflow, and they were stretched to the group's height). The transition runs only with both bands in view and match-element supported, never under Reduce Motion (router.js `shouldMorph` and `morphPage`); otherwise the page swaps at once. Only one `.page-header` may be in the DOM at a time (a duplicate name skips the transition).
- **Loading states** ("Warm Shelf"; all loader CSS is in the **Loading & motion** section of `app.css`, with tokens `--color-skeleton` `#efebe4`, `--skeleton-sheen`, `--loader-delay` 300ms, `--loader-delay-gate` 350ms, `--ease-morph` (the band morph's curve), `--ease-hop` on `:root`). Never add a plain "Loading…" paragraph or swap a button's text for "Saving…". Use `Skeleton` (or `.skeleton` + `.bone` markup on the real containers, with `.skeleton-sheen` on each row or card) for content waits, `BusyLabel` inside buttons for actions, `RouteProgress` for lazy chunks (a cold load's `{:pending}`, or a page change waiting on its chunk while the old page stays up), and `.list-refreshing` for a list refreshing in place. Placeholders appear in one step only after 300ms (350ms for header and auth gates; `@keyframes arl-appear` run for `0s` after the delay, fill `both`), leave instantly, and announce through `LoadingStatus` only after 1s; skeleton shapes are `aria-hidden` and no `aria-busy` goes on an ancestor of a live region. Content that replaces a loader renders at once, with no reveal; images use `revealOnLoad`. Copy is playful but short (`inventory.loading` "Stocking the shelves…", `loading.page` "Turning the page…"); busy verbs stay literal and end in `…`. One `@media (prefers-reduced-motion: reduce)` block in that section removes the sheen, translates and hops (bones flat, hairlines become a static bar breathing in opacity, busy dots static, tiles don't lift); page changes need no rule there, because router.js runs no view transition under Reduce Motion.
- **Motion** (since 2026-10-09): nothing fades except the few kept below. On a page change only the title band's colour and size animate; its words and the rest of the page switch at once, and a change that can't morph both bands (either one out of view, Reduce Motion, no `match-element`) swaps at once with no transition (see **Page layout** and the router entry). Content that replaces a loader, homepage sections, inventory cards, placeholders (one step after their delay), busy labels, photo previews and the boot card appear in one frame, and Kimchi's bubbles spring up without a fade and leave in one frame; images stay hidden over their frame's fill until decoded, then swap in (`revealOnLoad`). Motion that isn't a fade stays: the loaders (hairline, refresh segment, sheen, hopping dots), tile lifts and press scales, the skip link, and Kimchi's spring pop-in, stack slide, wiggle and hover growth. Fades kept on purpose: the item overlay's success status line (shown 5 s, then `.card-status.fade-out` over 0.5 s), the calendar highlight ring (`box-shadow` 0.25 s), the 150 ms hover and focus colour eases, and, under Reduce Motion, the hairline and refresh bar breathing in opacity. New UI follows the same rule: no `in:` / `out:` fades and no opacity transitions.
- **Design F** (since 2026-11-05, not deployed): the `/account` agenda (`AccountAgenda` and its cards), the expert request form and overlay, and the `/admin` lists share one flat look, kept in the **Design F** block of `app.css` (with its tokens `--f-hover`, `--f-press`, `--f-past-fill` / `-border` / `-text` (grey for past and disabled things, 6:1), `--f-lavender-tint`, `--f-plum-hover`, `--f-plum-tint`, `--f-focus-halo` on `:root`). The shared rules it restyles stay where they are defined (stickers, `.consultation-field*`, `.admin-item-list` / `-row`, the admin tiles and toggles, `.btn-approve` / `.btn-remove`, the expert overlay's header). Rules: no shadows except the field focus halo; 2px `Dark` borders; hover changes colour and never lifts; a press moves a control down 1px (`translateY(1px)`). **Stickers:** `.consultation-status` is a straight sticker (2px `Dark` border, radius 3px, Inter 800 0.75rem uppercase, no tilt), on `/account` and `/admin`: Lemon for needs-you, soon and starts-today; Pear for in progress and scheduled; Lavender for pending and no-email; Grape with Light text for live; Plum with Light text for overdue; white for confirmed, follow-up, staff and your item; grey (`--f-past-*`) for cancelled, refused, ended, completed, withdrawn and declined. **Buttons:** `.action-btn` (white, 2px `Dark` border, radius 10px, at least 44px tall; `[aria-expanded='true']` turns it `Dark`), `--primary` (Lemon; `Dark` with Lemon text on hover and while busy), `--danger` (Plum, only the Yes of a destructive question), `--danger-quiet` (white with a Plum edge, for buttons that open one), `--block`, `--icon`; `.btn-approve` looks like `--primary` and `.btn-remove` like `--danger-quiet`; the secondary buttons are restyled only under `.admin-page` and `.account-page` (`.btn-secondary`, `.btn-header--secondary`), never site-wide. **Pieces:** `.f-title` (Ringold section title over a 3px rule), `.f-label` (the one uppercase label: week headings, read-only field labels, **Who sees this**), `.f-field-label` (a label over an input, a bold sentence), `.f-card` (white, 2px `Dark` border, radius 12px), `.f-note` (what a member typed, line breaks kept; `.consultation-field__value` looks the same), `.f-strip` (a Lavender-tint band of context; `--in-card` runs edge to edge along a card's foot), `.f-hl` (a Lemon highlighter, at most three on a page), `.f-disclosure` (a bold text toggle with a plus that turns to a minus), `.f-field` (2px border, radius 10px, 1rem text so iOS doesn't zoom; applied by scoping to `.agenda` and `.consultation-form`, so `MeetingTimePicker`, `ConfirmationMessage` and `ReservationMessageForm` take it there), `.inline-confirm*`, `.more-menu*`, and the agenda's `.agenda*` / `.needs-you*` layout.
- Fonts referenced as `/assets/fonts/...` (served by Express from `src/assets/fonts`, not bundled by Vite). Titles (`h1`–`h3`, `.panel-title`, `.modal-header h2`, `.inventory-content h3`, `.home-category__name`, `.how-this-works-step__number`) are uppercase **Inter Bold (700)** through `--font-display` (an alias of `--font-body`); every rule that uses `--font-display` also sets `font-weight: 700`. The exceptions are each page's title, the `h1` in its `.page-header` band (homepage, inventory, How it works, About, Privacy, Account, Admin, 404): `.page-header h1` sets it in **Ringold Sans** through `--font-brand` at `font-weight: normal` (Ringold has a single weight, so 700 would be a synthesized bold); design F's section titles, `.f-title` (the `/account` agenda's **Needs you** and **Coming up**, the request form's **Request a consultation** and **Request sent**), also in Ringold at `font-weight: normal` (2.5rem, 1.875rem on phones; `.f-title--sm` 1.75rem) over a 3px `Dark` rule; and the expert overlay's name, Inter 800 in its real case (not uppercase, never Ringold), since it is a person's name. Two `@font-face` rules point at WOFF2 Latin subsets: `inter/Inter-latin.woff2` (from the variable TTF with `slnt` pinned to 0 and `wght` limited to 400–900, since app.css uses 400–700 and `<strong>` inside 600/700 text resolves to 900) and `ringold/Ringold-Sans.woff2`. Inter is preloaded from `index.html` on every page; Ringold (16 KB) is preloaded on every HTML response by the SSR shell in `server.js` (`BRAND_FONT_PRELOAD`), since every page's title uses it. Both keep all OpenType layout features and declare the same `unicode-range`: U+0000-017F, U+02BB-02BC, U+02C6, U+02DA, U+02DC, U+2000-206F, U+20AC, U+2122, U+2190-2193, U+2212, U+2215, U+2713, U+FEFF, U+FFFD (Google's "latin" set plus Latin Extended-A, arrows, and every non-ASCII character in `locales/`, `content/` and `src/` except emoji, which neither font has). Characters outside it (e.g. Cyrillic or Vietnamese in a catalogue title) fall back to the system font. To regenerate (fonttools + brotli, outside the repo): `fonttools varLib.instancer Inter-VariableFont_slnt,wght.ttf slnt=0 wght=400:900 -o inst.ttf`, then `pyftsubset <font> --unicodes="<range above>" --layout-features='*' --name-IDs='*' --flavor=woff2`. A regenerated font needs a **new file name** (and updated CSS + preload: `index.html` for Inter, `BRAND_FONT_PRELOAD` in `server.js` for Ringold), because `/assets/fonts` is cached for 7 days. Ringold Sans is licensed through TypeNetwork (licence ID in the font's name table).
- Brand colors from `docs/Apathy_is_Boring_Brand_Guidelines.md` as CSS variables in `:root` (`--color-light`, `--color-dark`, `--color-lemon`, `--color-lavender`, `--color-plum`, `--color-mint`, `--color-pear`, `--color-grape`). White-dominant UI: white/`Light` surfaces, `Dark` text, `Lemon` primary actions, `Mint` reserve buttons. Contrast pairings follow the brand matrix (Group A backgrounds with Group B foregrounds).
- **Links** default to Mint (`a { color: var(--color-mint) }` in `app.css`), so a link without a class colour never shows the browser's blue or visited purple; class rules that set a colour win.
- **Focus indicators** are 2px outlines in `Dark`, `Mint` or `Grape`, never `Lemon` (Lemon is 1.34:1 on white and 1.28:1 on `Light`, below the 3:1 non-text minimum). The one exception is a link on a dark title band (Mint, Dark or Plum), whose ring is its `--band-link` Lemon, which is well above 3:1 on those bands. Mint is 11.42:1 on white, 10.85:1 on `Light` and 8.50:1 on Lemon; Grape is 9.72 / 9.24 / 7.23:1. Card links, the FES logo link and the Kimchi bubble controls use Mint; the Kimchi avatar and status dot, which float over page content (including the Mint **Reserve** buttons), use a two-tone ring: a Mint outline at `outline-offset: 0` with a 4px white `box-shadow` halo outside it (Mint and white are 11.42:1 apart, so one tone is at least 3.38:1 against any background); text fields keep the Grape border + 15% Grape halo (`input:where(:not([type='checkbox'], [type='radio'])):focus`, kept at `input:focus` specificity so component rules can still override it; the meeting-time field uses it too); checkboxes, which paint no border, keep an outline (`.auth-opt-in input[type='checkbox']:focus-visible` is Grape). Headings focused from script (`h1[tabindex='-1']`) show no ring. Design F's controls (`.action-btn`, `.more-menu__item`, `.f-disclosure`, the inline questions' buttons) use a 3px Grape outline with a 3px offset (inset on menu items), and its fields a Grape border with an 18% Grape halo (`--f-focus-halo`, the only shadow in F); Lemon and Pear stickers are never focus colours.
- **Fixed corner widget:** Kimchi (bottom-right) sits at `--corner-widget-bottom` (0.75rem + `safe-area-inset-bottom`; the right offset adds the side inset). `--corner-widget-clearance` (that plus 4.75rem, clearing the 4rem avatar) is both `.app`'s `padding-bottom` and `html`'s `scroll-padding-bottom`, so the last content scrolls clear of Kimchi and keyboard focus scrolls controls above it. (The bottom-left FES badge was removed on 2026-10-06; FES is credited in the site footer, which ends inside `.app`, so this padding sits under the footer's copyright line.) On short viewports (`@media (max-height: 500px)`: landscape phones, 400% zoom) Kimchi shrinks to a 2.75rem avatar with narrower bubbles and only the newest one showing (styles in `KimchiNotification` / `KimchiBubble`); the status dot keeps its 24 px target.

## Svelte conventions in this repo

- Svelte 5 runes (`$state`, `$props`) used in components. Auth state (`session`, `authReady`) uses classic `writable` stores from `src/lib/auth.js`; `HeaderAuth.svelte` subscribes via `$session` / `$authReady`.
- Callback props instead of `createEventDispatcher` (e.g. `oncreated`, `onAddItem`).
- Modal opened via `bind:this` on `AddItemModal` and calling `addItemModal.open()`.
- `initAuth()` is called from `HeaderAuth.svelte` `onMount` (not `App.svelte`).
- `AuthModal.svelte` (register) and `SetPasswordModal.svelte` enforce a minimum password length of 8 client-side (`PASSWORD_MIN_LENGTH` in `auth.js`); login does not check length.
