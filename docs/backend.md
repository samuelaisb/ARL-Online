# Backend, environment and deploy

`server.js` (static assets, data, the API table, email, Slack, GA, reminders), environment variables, Docker / Cloud Run and Google Search Console. The project map is `AGENTS.md`; the git and deploy rules agents follow are in `CLAUDE.md`. Moved here from `AGENTS.md` on 2026-11-05.

## Server overview

`server.js` holds the app: middleware, routes, when emails and Slack posts go out, and the request-driven passes. What they say lives in `server/` (since 2026-11-05): `server/email-payloads.js` (every email's subject, HTML and text), `server/ics.js` (calendar invites), `server/slack-messages.js` (Slack payloads), `server/format.js` (shared formatting) and `server/site.js` (`SITE_URL`, item page URLs, `FROM`, `EMAIL_REPLY_TO`, `CONTACT_TO`). The first middleware 301s `www.<host>` (for the `SITE_URL` host and `PRODUCTION_SITE_ORIGIN`'s host) to the same path and query on the apex; other hosts (localhost, `*.run.app`) pass through. Uses `helmet` for security headers, `compression` right after it (Brotli/gzip for HTML, JSON, JS and CSS; Cloud Run's front end does not compress, and images/WOFF2 are skipped by type), `app.set('trust proxy', 1)` for correct rate limiting behind Cloud Run, and admin audit logging (`[admin-audit]` console lines on every admin mutation).

**Content Security Policy** — `script-src` has **no `'unsafe-inline'`**. At startup, `extractInlineScriptHashes()` scans the inline executable `<script>` blocks in `dist/index.html` (currently only the Google Analytics gtag bootstrap) and adds a `'sha256-…'` hash for each to `script-src`; the per-request SEO injection only adds JSON-LD data blocks or external scripts, so the same hashes cover every HTML response. To add another inline script, put it in `index.html` and rebuild — the hash list refreshes on server start (restart after `npm run build`). External script sources: `'self'`, `https://*.googletagmanager.com`, and `https://plausible.io` when `PLAUSIBLE_DOMAIN` is set. `connect-src` includes `SUPABASE_URL`, GA collection hosts, and optional Plausible; `img-src` allows `'self'` (which covers `/media/items/...` photos), `data:` (Vite-inlined images, Leaflet's inlined control icons; legacy item data URLs), GA beacon hosts and the map tile hosts (`MAP_TILE_HOSTS` from `src/lib/map-tiles.js`: `https://tile.openstreetmap.org`, `https://api.thunderforest.com`); bike-share data comes through our own `/api/bike-share`, so `connect-src` needs no new host; `style-src` still allows `'unsafe-inline'` (Svelte inline styles); `frame-ancestors 'none'`.

**Dependency hygiene** — `package.json` `overrides` pins `qs` to `^6.16.0` because Express 4.x still declares `~6.15.x`, which has open advisories. Run `npm audit --omit=dev` before deploying; it must report 0 vulnerabilities. Remove the override once Express 4 (or a move to Express 5) ships a patched range.

## Static assets

- `GET /config.js` — runtime public client config (`window.__ARL_ENV__`: `SUPABASE_URL`, `SUPABASE_API`, `SITE_URL`); `Cache-Control: no-store`.
- `GET /assets/*.js|css`, `/robots.txt`, `/favicon.ico`, `/favicon-16x16.png`, `/favicon-32x32.png`, `/apple-touch-icon.png` from `dist/` — `express.static` with **`index: false, redirect: false`**, so it serves only real files (hashed JS/CSS, `robots.txt`, the icons copied from `public/`). It never serves `index.html` for `/` and never 301-redirects `/about` → `/about/`. Files directly in `dist/assets/` (Vite's content-hashed output) get `Cache-Control: public, max-age=31536000, immutable`; other dist files (`robots.txt`, the icons, the `public/assets/fonts` copies) get `public, max-age=3600`; a direct `/index.html` gets `no-cache`.
- `/assets/*` (anything the asset statics did not serve, e.g. a chunk from an earlier deploy) — `404` `text/plain` `Not found.`, never the SPA shell.
- `GET /media/items/:id/:file` — uploaded photos (stored as data URLs in `inventory_items.image`). Outside `/api/` so crawlers and link previews can fetch og:image (`robots.txt` blocks `/api/` apart from the two public inventory reads). Loads only that item's `image`; 404 (`text/plain`) when the item is missing or the image is not a JPEG/PNG/WebP/GIF data URL (seed paths, SVG). When `:file` is the current `{hash}.{ext}` it sends the decoded bytes with that `Content-Type`, `Cache-Control: public, max-age=31536000, immutable` and `Cross-Origin-Resource-Policy: cross-origin`; otherwise `302` to the current URL with `Cache-Control: no-cache`. Other `/media/*` paths 404.
- `GET /api/*` (unmatched) — JSON `404 { error: 'Not found.' }` (`app.all('/api/*')` before the catch-all), so typo'd or removed API paths do not return the SPA shell as HTML 200.
- `GET *` catch-all — every HTML route (`/`, `/equipment`, `/about`, `/privacy`, `/howthisworks`, `/{tag}/{slug}`, `/admin`, `/account`, `/join`, trailing-slash variants) is served from the in-memory `dist/index.html` template with per-request SEO injection via `seo-server.js` (single title/description/OG/Twitter set, canonical without trailing slash, hreflang, `<html lang>` for the resolved locale, Organization/FAQ/Product JSON-LD). `/admin` and `/account` also get `X-Robots-Tag: noindex, nofollow` and no JSON-LD. **404s:** a path that is not a known app path (`isKnownAppPath` in `src/lib/item-routes.js`, e.g. `/how-it-works`, `/Equipment`, `/fr`) and a `/{tag}/{slug}` whose slug does not exist get status **404** with the same SPA shell, a `noindex, nofollow` robots meta, the localized `seo.not_found_title` and no JSON-LD; the client then shows its not-found view (or the overlay's **Item not found**). A failed item lookup (Supabase error) stays 200. Sent with `Cache-Control: no-cache`, because the shell names the current hashed bundles. On `/{tag}/{slug}` routes the shell also gets `<link rel="modulepreload" crossorigin href="/assets/ItemDetailPage-[hash].js">`, so a deep link fetches the overlay chunk alongside the entry instead of after it runs. `server.js` finds that file once at startup (`findItemDetailChunkPreload`, matching Vite's default `[name]-[hash].js` name in `dist/assets`); with no match the hint is left out.
- `GET /robots.txt` — static file from `dist/` (copied from `public/` at build). Allows `/`, `/api/inventory` (exact, via `$`) and `/api/inventory/by-slug/`; disallows `/api/`, `/admin`, `/account`. Google applies the longest matching rule, so the rest of `/api/` stays blocked. The two allowed reads are what the rendered item and category pages fetch; blocking them made Google render item pages as **Item not found** with the default title.
- `GET /sitemap.xml` — dynamic sitemap (static routes + all items as `/{tag}/{slug}` with `lastmod` from `createdAt`); `Cache-Control: public, max-age=3600`.
- `GET /assets/fonts/*` from `src/assets/fonts/`.
- `GET /assets/brand/*` from `src/assets/brand/` (Apathy is Boring header logo, FES logo, both also in the site footer).
- `GET /assets/inventory/*` from `src/assets/inventory/` (seed images and `items.json`).
- **Caching rule:** these three mounts keep stable file names, so they are served with `Cache-Control: public, max-age=604800` (7 days). To change a font, brand image or seed photo, **add it under a new file name** and update the references; overwriting a file in place leaves returning visitors on the old copy for up to a week. Vite-built assets need nothing: their names change with their content.

## Data

- Inventory and reservations persist in **Supabase Postgres** via `src/lib/inventory-store.js` (service role key on the server). Apply `supabase/migrations/001_inventory.sql`, `002_reservation_approval.sql`, `003_lock_down_roles.sql`, `004_inventory_slug.sql`, `005_expertise.sql`, `006_consultation_scheduling.sql`, `007_expertise_copy.sql`, `008_consultation_follow_up.sql`, `009_admin_stats.sql`, `010_item_locations.sql`, `011_item_location_stations.sql`, `012_staff_bookings.sql`, `013_staff_booking_ga_events.sql` and `014_account_email_change.sql` before first run (or, when upgrading, before deploying code that needs them: 009 must be in place before the admin Members delete runs; 010 to 013 can follow the code, which shows the office, counts staff bookings under Members in Stats, and sends their GA event from the browser, until then; 014 is a database trigger with no app code). Then `015_item_owners_and_reminders.sql`, after 014 (re-run it if 014 is applied after it); it can follow the code, which until then has no owners and sends no reminders. Then `016_reservation_messages.sql`, **before** the code that uses it (without it messages can't be opened or sent) (**Expertise consultations → Schema**).
- Tables: `inventory_items` (`id`, `title`, `body`, `image`, `tag`, `slug`, `created_at`, `expert_email`, `long_body`, `location_id`, `owner_email`) and `reservations` (`id`, `item_id`, `start_date`, `end_date`, `status`, `user_email`, `time_slots`, `request_summary`, `meeting_at`, `zoom_meeting_id`, `zoom_join_url`, `zoom_password`, `cancelled_at`, `cancelled_by`, `follow_up_of`, `created_at`, `anonymized_at`, `booked_by_staff`, `ga_event`, `ga_event_at`, `reminder_email`, `reminder_email_at`), plus `item_views` (`item_id`, `day`, `count`: views per item per Montréal day, written only through `increment_item_view`). Unique index on `(tag, slug)`. RLS is enabled with no public policies — Express uses the service role (bypasses RLS). Migration `003_lock_down_roles.sql` revokes direct table access from `anon`/`authenticated`. Slugs are generated server-side at create/seed time from title (`src/lib/slug.js`); immutable after create; collisions within a tag append `-2`, `-3`, etc. `ensureInventory()` runs a once-per-process slug backfill (`ensureSlugsBackfilled()`) that is **decoupled from the `inventorySeeded` flag** — it always populates missing slugs on existing rows even when the inventory is already seeded, and retries on the next request if it fails (errors are logged, not swallowed, and never break the inventory read). `npm run backfill:slugs` triggers the same backfill on demand.
- **Public** API item shape (`GET /api/inventory`, `GET /api/inventory/by-slug/:tag/:slug`): `{ id, title, body, image, createdAt, tag, slug, longBody, reservations }` where `reservations` is `{ id, startDate, endDate, status }[]` — **`userEmail`, `expertEmail`, `timeSlots`, `requestSummary`, and `meetingAt` are never returned on public routes** (nor the admin-only `createdAt`, `anonymizedAt` and `bookedByStaff` of a reservation). `body` is the description (expertise: short list text). `longBody` is the expertise bio, or `null` on other tags. `image` is a `/media/items/{id}/{hash}.{ext}` URL for uploaded photos or the seed `/assets/inventory/...` path, never a data URL. Admin route `GET /api/admin/inventory` returns full items including `userEmail` + consultation fields on reservations and `expertEmail` and `ownerEmail` on items (same `image` mapping).
- `status` on reservations: `pending` (new member request), `reserved` (admin-approved, or consultation scheduled), `refused` (admin declined — dates freed), `cancelled` (consultation cancelled by member/expert/admin, an equipment/book/room reservation the member withdrew or cancelled from `/account`, `cancelled_by: 'member'`, one staff cancelled by deleting the member's account, `cancelled_by: 'admin'`, or one the item's owner cancelled from `/account`, `cancelled_by: 'owner'`), or legacy `available`. Admin deletes of equipment/book/room reservations are still hard deletes. A deleted member's rows keep their item, dates and status but lose `user_email`, `time_slots` and `request_summary` (`anonymized_at` set). New creates always use `pending` with member email from JWT.
- `pending` and `reserved` block calendar dates; only `reserved` marks the card **Unavailable** badge.
- **Tag-specific reservation rules** (enforced in `ItemCalendar` and `POST`/`PATCH` reservation APIs via `src/lib/reservation-rules.js`; ranges are inclusive):
  - **equipment** — Start must be a **Tuesday**; end is automatically the **following Tuesday** (+7 days). One-week block; pickup/drop-off hours message shown on the calendar.
  - **books** — Start must be a **Tuesday**; end is **four weeks later** (+28 days, also a Tuesday). One-month block; same pickup/drop-off message.
  - **rooms** — Flexible inclusive range on any days (existing two-click range selection). Members also give a start and end time (`<input type="time">`, end after start, the same hours on each day) and what the room is for (required, max 1000), checked by `validateRoomRequest` on both sides and stored in `time_slots` (`HH:MM-HH:MM`) and `request_summary`. The hours are information for staff: a request still blocks its whole days.
  - **expertise** — No calendar. Consultation requests store the submission date as both start and end; free-text `time_slots` (max 500 chars) and `request_summary` (max 2000 chars) are required instead. Date collisions never apply (multiple members can request the same expert). Admin approval requires `meetingAt` (ISO timestamp, stored in `meeting_at`).
- Calendar UI for equipment/books: only Tuesdays are selectable; clicking a Tuesday selects the full fixed block. Equipment and books modals show localized pickup/drop-off hours (10am–5pm Tuesdays).
- **Stored** `image` (`inventory_items.image`) is either a data URL from the client compressor (WebP preferred, JPEG fallback; the server also accepts PNG and GIF) or a path like `/assets/inventory/images/...` for seeded MyTurn items. Write paths (`POST`/`PATCH /api/inventory`, `POST`/`PATCH /api/account/mentor-profile`) reject a data URL over 2,000,000 characters with **413** `{ error, code: 'image_too_large' }` and any other format or path (including SVG) with **400** `{ error, code: 'image_invalid' }`. Only the admin routes accept a seed path, and only a short plain one (at most 200 characters, `[A-Za-z0-9._-]` segments, no `..`); the member routes accept uploaded data URLs only. A `/media/items/...` URL is never stored: on the two `PATCH` routes, that item's own `/media/items/{sameId}/...` URL (any hash) means "photo unchanged"; elsewhere it is `image_invalid`.
- **Sent** `image`: every response that carries an item maps a stored data URL to `/media/items/{id}/{hash}.{ext}` (`hash` = first 16 hex of SHA-256 of the stored data URL; `ext` from the MIME: `jpg`, `png`, `webp`, `gif`), so a new photo gets a new URL and the old one redirects. The SSR head uses the same URL, made absolute, for og:image, twitter:image and the Product JSON-LD `image`. Storage is unchanged (no migration); `/api/inventory` drops from about 1.1 MB to about 11 KB of JSON with the current catalogue.
- Seeding runs via `ensureInventory()` in `inventory-store.js` (no-op after first successful seed via `inventorySeeded` flag). If the DB is empty: import `data/inventory.json` when present, else insert 9 seed items from `src/assets/inventory/items.json`.
- Every reservation/item write (`addReservation`, `approveReservation`, `scheduleConsultation`, `cancelConsultation`, `cancelReservationForMember`, `cancelReservationByAdmin`, `anonymizeReservationsForEmail` (one item at a time), `refuseReservation`, `removeReservation`, `patchReservation`, `rescheduleReservation`, `rescheduleConsultation`, `updateExpertiseItem`, `deleteInventoryItem`) runs inside an in-process per-item lock (`withItemLock`) around read + write (single Cloud Run instance only; not safe across replicas). A refuse/delete that arrives during a schedule's Zoom call waits for it to finish.
- Seeded item IDs use the format `myturn-{sourceId}` when `sourceId` is present in the seed file.
- One-time upsert from legacy JSON: `npm run migrate:inventory` (or rely on auto-import when the DB is empty on first `GET /api/inventory`).

## Email (Resend)

- `RESEND_API_KEY` is lazy-initialized: the server starts without it (logs a warning); member approval/refusal emails fail with a clear error when sent if unset.
- Every app email (reservation decisions, welcome, contact form, consultation request / scheduled / moved / cancelled, team cancellations, new dates, day-before reminders, messages about a booking, admin password reset) is rendered by `renderBrandedEmail()` in `src/lib/email-brand.js`: full HTML document plus a plain-text part. The header wordmark is text, not an image, so it shows on open instead of popping in (and shows when images are blocked). Layout: Mint header, uppercase Inter headline, Lemon button with Dark text, Grape links, dotted divider, Dark identification footer. No unsubscribe link (these are transactional). Copy stays English-only.
- **Routes wait for their emails before responding** (`settleNotifications()` in `server.js`), because Cloud Run can throttle CPU once a response is out and stall sends still in flight. A failed email (Resend error, missing key, or the 10 s cap `EMAIL_SEND_TIMEOUT_MS`) is logged and never turns a saved action into an error: approve, refuse, reservation create (expertise), schedule, cancel, the admin deletes that cancel consultations or upcoming member reservations, and the admin member delete (when it cancelled anything) add `emailSent: true|false` to their JSON. The admin password reset is the exception: its email is the whole action, so a failed send is a 502 (`password_reset_failed`) and success is `{ emailSent: true }`; so is a message about a booking (`POST /api/reservations/:id/message`: 502 `message_send_failed`). The host's approve, refuse, new dates and cancel on `/account` and the consultation move add `emailSent` like the admin routes. `true` means there was at least one email and Resend accepted all of them. A Resend 429 (`rate_limit_exceeded`; default limit 2 requests per second) is retried once after 1 s (`EMAIL_RATE_LIMIT_RETRY_MS`); nothing else is retried. Admin item deletes notify in paced rounds (`settleNotificationRounds()`, at least `EMAIL_PACING_MS_PER_EMAIL` = 0.5 s per email per round). The client reads `emailSent` only to drop an "emailed" claim: `AdminPanel` (approve, refuse, deletes, follow-up), `AgendaConsultationCard` (schedule, cancel, follow-up, move) and `AgendaBookingCard` (the host's approve, decline, new dates, cancel; also when the row has no member email) show Kimchi's `_plain` bubbles when it is `false` (the cancel also checks `otherPartyEmailed`), and their hidden status lines add an "emailed" note only when it isn't `false` (`AdminPanel`: only when it is `true`); there is no warning UI.
- **Reply-To:** every app email sets `replyTo: EMAIL_REPLY_TO` (default `CONTACT_TO`, `samuel@apathyisboring.com`) except the contact form (the visitor). Messages about a booking from `/account` use the library's too (since 2026-11-05; before, the sender's, which gave members the owner's address): the other side answers in the booking's conversation on `/account`. `activistresourcelibrary.com` has no MX record, so replies to `noreply@` would otherwise be lost.
- **Calendar invites:** `buildConsultationIcs` writes `SEQUENCE` as the time it was built in seconds since 1970 (`Math.floor(Date.now() / 1000)`), for `REQUEST` and `CANCEL` alike, since nothing stores a revision: calendars keep the highest `SEQUENCE` for a UID, so a moved meeting's invite, a handover invite or a cancellation always replaces an earlier one, and an old email opened late can't undo it. It fits RFC 5545's integer until 2038.
- **Day-before reminders:** "Your reservation is coming up!" (rooms, equipment and book pickups → the member) and "Your consultation is coming up!" (→ member and mentor, with the Zoom link, no `.ics`), sent by a request-driven pass about a day before the start (see **Day-before reminders** below; `docs/automated-emails.md` trigger 12).
- **Messages about a booking** (`docs/automated-emails.md` triggers 13 and 14): one email per message, to the host (`itemOwnerEmail`, else `CONTACT_TO`) or to the member, never stored. **Owner actions** on `/account` reuse the admin emails (approval, refusal, team cancel with an optional **Message from the library team**) and add **New dates for your reservation** (trigger 16) and **Consultation moved** (trigger 15). New subjects go through `emailSubject()`, which turns control characters into spaces so a title or typed address keeps the subject on one line.
- New pending reservation requests on equipment/books/rooms do **not** send email — admins are notified via the Slack webhook only. **Expertise consultation requests** send the member a "consultation request received" email and the expert (item `expert_email`, when set) a "new consultation request" email on submit.
- Member approval/refusal emails go to the reservation `userEmail` (from JWT at create time; skipped with log if missing). No env-based `EMAIL_TO` fallback. Expertise approvals schedule the consultation and send the scheduled emails (Zoom link + `.ics`) to member and expert. The member message includes "This project is funded by YES Employment." and the data-sharing form link (**placeholder `CONSULTATION_DATA_FORM_URL` in `server/email-payloads.js` — replace before launch**). A funder logo strip renders above the footer only when `EMAIL_FUNDER_LOGO_URL` is set.
- Member welcome email on sign-up: `POST /api/auth/welcome-email` (client fire-and-forget after sign-up or first sign-in within 7 days); links to `/howthisworks` and `/about`; deduped via `user_metadata.welcome_email_sent`.
- About-page contact form emails go to `samuel@apathyisboring.com` with `replyTo` set to the submitter's email (`POST /api/contact`; requires `RESEND_API_KEY` at send time).
- Equipment, book and room approval emails have a **Where** row with the item's own place (`item.location`: name, street, then `Montréal QC H2T 1S1` on three lines), a **Getting there** row with its English transit note, and a **Get directions** link (Google Maps, transit) before **Browse the library**, so the plain-text part carries the URL too. Equipment and books add "Pickups and drop offs are between 10am and 5pm on Tuesdays at the address above." and close with "We look forward to seeing you at pickup."; rooms close with "If anything changes, just reply to this email." If the item's place can't be resolved (an unknown `location_id` other than the office's), the email has no Where row and asks the member to reply for the address instead of guessing (equipment and books: the pickup sentence without the address; rooms: "Reply to this email and we will send you the room's address."). Reservation emails write dates out in English (`formatReservationDates()`).
- Admin deletes of an equipment, book or room reservation (or of its item) email each member whose reservation was `pending`, or `reserved` and not yet over: "Your reservation for {item} ({dates}) was cancelled by the Activist Resource Library team", with a link to the category page (`buildReservationCancelledByTeamEmailPayload`). A member withdrawing or cancelling their own reservation from `/account` gets no email.
- Admin **Members**: deleting a member (`DELETE /api/admin/users/:id`) sends the same team-cancel email for each of their equipment, book or room rows that is `pending`, or `reserved` and not over (worded from the status before the cancel), and the consultation-cancelled emails ("The Activist Resource Library team cancelled …", to both people) for each pending or not-yet-held consultation, in paced rounds, before the account is anonymized and deleted. Their past-dated pending requests are cancelled without email. **Send password reset** (`POST /api/admin/users/:id/password-reset`) emails the account Supabase's one-time recovery link: subject "Set a new password for the Activist Resource Library", button **Choose a new password**, `EMAIL_WHY.passwordReset`; when `RESEND_API_KEY` is unset no link is made. Rename and suspend send nothing. Details: `docs/automated-emails.md` (triggers 7–9).
- All Resend email links use `SITE_URL` (or `VITE_SITE_URL`), falling back to `https://activistresourcelibrary.com` when unset — member decision emails link to the item and library home.
- `EMAIL_FROM` defaults to `noreply@activistresourcelibrary.com`; legacy `onboarding@resend.dev` in env is ignored at runtime.
- Footer contact (`orgContact` in `email-brand.js`): Apathy is Boring · address · phone · apathyisboring.com. This is the sender's postal line (and the welcome email's pickup line), not an item's place, which comes from `item_locations`. Optional env overrides: `ORG_ADDRESS`, `ORG_PHONE`. `npm run cloud:build` passes `ORG_PHONE` when set; it does not pass `ORG_ADDRESS` (the comma breaks gcloud's env list).

## Slack reservation webhook (optional)

When `SLACK_RESERVATION_WEBHOOK_URL` is set, a successful `POST /api/inventory/:id/reservations` POSTs text-only JSON to the Slack workflow trigger (5s fetch timeout). The route waits for the post before it responds; failures are logged and never fail the reservation. **Staff alerts** use the same trigger through `notifySlackAlert()` (both go through `postSlackWorkflow()`): the same 14 keys, unused ones as `''`, with `status` naming the event and `request_summary` holding one readable sentence. Today the alerts are `mentor_profile_published` and `mentor_profile_updated` (after `POST`/`PATCH /api/account/mentor-profile`; `user_email` and `expert_email` are the account email, `start_date`/`end_date` today's date key, `reservation_id`/`time_slots` empty) `member_signed_up` (once per account, from `sendWelcomeEmailIfNeeded()` when it claims the welcome email; `user_email` the member, item fields empty) and `reservation_cancelled_by_member` (a member cancelled an approved equipment, book or room booking from `/account`; `reservation_id`, `start_date` and `end_date` are that reservation's, `user_email` the member). Every post also carries `message`, the full Slack text built by the server (`reservationSlackMessage()` for new requests, the event emoji + sentence for alerts), and the workflow message is just `{message}` plus a **Review** button linked to `{admin_url}`. Configure the Slack workflow trigger to accept these variables:

| Variable | Content |
|----------|---------|
| `message` | The whole message to post (plain text with line breaks); the workflow shows only this |
| `item_id` | Inventory item id |
| `item_title` | Item title |
| `item_body` | Item description |
| `item_tag` | `equipment`, `books`, `rooms`, or `expertise` |
| `reservation_id` | New reservation UUID |
| `start_date` | Reservation start (`YYYY-MM-DD`; submission date for expertise) |
| `end_date` | Reservation end (`YYYY-MM-DD`; same as start for expertise) |
| `status` | `pending` on create; `member_signed_up` / `mentor_profile_published` / `mentor_profile_updated` / `reservation_cancelled_by_member` / `consultation_follow_up` for staff alerts |
| `user_email` | Member email from JWT |
| `time_slots` | Member availability free-text (expertise); a room request's hours as `HH:MM-HH:MM`; else empty string |
| `request_summary` | Consultation topic summary (expertise); what a room is for (rooms); else empty string. For staff alerts, the alert sentence |
| `expert_email` | Expert contact from the item (expertise only; else empty string) |
| `admin_url` | Absolute link to `/admin` for reviewing the request |

Mutating routes return 401 without a valid JWT, 403 `{ code: 'account_suspended' }` when the account is suspended, and 403 when admin is required but the email is not `@apathyisboring.com` or the admin email is not confirmed.

## Staff bookings in GA (optional)

GA can't take an event back, so a staff booking's `booking_request_sent` waits about an hour and is sent by the server (GA4 Measurement Protocol), only if the booking wasn't a test: the same tests **Stats** leaves out. Member requests still send theirs from the browser at once.

- **On:** both `GA_MEASUREMENT_ID` and `GA_API_SECRET` set, the deployed service (`NODE_ENV=production` or `K_SERVICE`, as for item views: a laptop on the production `.env` neither queues nor sends) and migration 013 applied. Otherwise `POST /api/admin/inventory/:id/reservations` answers `gaEventQueued: false` and **Create Reservation** sends the event from the browser at once, as before, so no order of deploy, env vars and migration loses or doubles an event (an `/admin` tab opened before the deploy runs the old form, which always sends from the browser: at most one double count).
- **Queue:** the booking is saved with `reservations.ga_event = 'pending'` (013), so it survives deploys and restarts.
- **No timers:** Cloud Run throttles CPU between requests, so a middleware in `server.js` runs `sendDueStaffBookingEvents()` on whatever request comes in, at most every 10 minutes per instance (`GA_EVENT_PASS_INTERVAL_MS`), and that request waits for it, 3 s at most (`PASS_REQUEST_WAIT_MS`, shared with the reminder pass; a longer pass carries on in the background). Chosen over a Cloud Scheduler call to a protected route: nothing more to set up or secure, and the work always runs inside a request. The cost: the event goes at the first request after the hour (crawlers and staff make that minutes), and a booking would expire unsent if the site got no request for 71 hours.
- **The pass:** `listPendingGaEvents` loads up to 50 `pending` rows made at least an hour ago (`TEST_CANCEL_WINDOW_MS`), with only the item's tag and title, never the email. Each is moved with `moveGaEvent(id, from, to)`, a conditional update: older than 71 h → `expired` (warning); a test cancellation (`isTestCancellation`, cancelled less than an hour after it was made) → `skipped`; otherwise claimed `pending` → `sending` (so a second instance or revision can't send it too), sent with `timestamp_micros` = when it was made, then `sent`. A failed send goes back to `pending` and retries next pass; a row left in `sending` (a crash or a failed update after the send) is never sent again, so a lost event beats a double one. A booking deleted from admin is gone and never sent; one cancelled after the hour but before the pass is sent, because Stats counts it too. Each send logs `[ga] Sent booking_request_sent for staff booking <id>`.
- **Checking it:** the event is dated an hour back, so it won't show in Realtime; look at Reports → Engagement → Events (`booking_source` = `staff`) the next day, or at the row's `ga_event` / `ga_event_at` in Supabase. The payload passes Google's validation server (`/debug/mp/collect`, which records nothing).

## Day-before reminders

About a day before a confirmed (`reserved`) booking starts, the member gets "Your reservation is coming up!" (rooms, equipment and book pickups) or "Your consultation is coming up!" (mentor meetings, to the mentor too); `docs/automated-emails.md` trigger 12. When a booking starts is `reservationStartsAt()` (`reservation-rules.js`): a consultation's `meetingAt`; a room's first day at its start time; a pickup's (or a room without hours) first day at 10:00, Montréal time.

- **On:** `RESERVATION_REMINDERS_HERE` = `RESEND_API_KEY` set and the deployed service (`NODE_ENV=production` or `K_SERVICE`), so a laptop on the production `.env` sends none. Before migration 015 the pass finds nothing (one warning).
- **Request-driven, like the GA pass:** the same middleware starts whichever pass is due, each with its own started-at and in-flight state and at most every 10 minutes per instance (`REMINDER_PASS_INTERVAL_MS`), and the request waits for the passes it started together, 3 s at most (`PASS_REQUEST_WAIT_MS`). No timers or Cloud Scheduler: if nobody reaches the site between 24 h and 1 h before a start, that booking gets no reminder.
- **Due:** more than 1 h and at most 24 h before the start (`isReminderDue`, `REMINDER_LEAD_MS`, `REMINDER_MIN_LEAD_MS`). `listReminderCandidates(now)` loads at most 50 consultations (`meeting_at` in that window) and 50 other bookings (`start_date` today or tomorrow in Montréal, filtered in JS), all `reserved` with `reminder_email` null, ids and tags only.
- **The pass** (`sendDueReservationReminders()` in `server.js`): first `releaseStaleReminderClaims()` hands back `sending` claims older than 30 minutes (`REMINDER_CLAIM_STALE_MS`; a pass that stopped mid-way). Then, per candidate, `claimReminder()` (null → `sending`, stamped, only if still reserved and unclaimed, so two passes can't both send it), re-read with `findReservationWithItem`: no longer reserved, or moved out of the window → released to null (a new time is picked up when it is due); already started → `skipped`; otherwise `buildReservationReminderEmailPayloads()` and each email sent on its own (`sendEmailPayloads([payload], 'Reservation reminder')`), paced `EMAIL_PACING_MS_PER_EMAIL` (0.5 s) apart across the pass. Any email accepted → `sent` (log `[reminder] Sent reminder for reservation <id>.`); none accepted → released for the next pass; nobody to email → `skipped`; an error → logged and released. A failing `settleReminder` is logged and leaves the row at `sending` for the stale release; it doesn't stop the pass. **Time box:** no new claim after 1.5 s of a pass (`REMINDER_PASS_CLAIM_WINDOW_MS`), so a consultation's two paced emails still fit in the request's 3 s wait; the rest wait for the next pass.
- **Confirm or move:** a booking confirmed or given a new time less than a day before its start gets no separate reminder: the confirmation or "moved" email is its reminder. After each one (admin approve, `runScheduleConsultation`, staff Create Reservation, follow-up, the owner's approve and new dates on a confirmed booking, consultation move) the route calls `setReminderState(id, reservationStartsAt(…))`: `skipped` within 24 h, else null, also after a reminder for the old time went out, so the new time gets one. Then `restoreReminderIfNotEmailed(reservation, tag, emailSent)`: when that email didn't all go out (`emailSent !== true`) and the booking is reserved, the state goes back to null so the pass still reminds the member. The admin `PATCH` of a reservation (API only, no email) uses `setReminderState(…, { notified: false })`, which always writes null. New rows start null.
- **Checking it:** `reservations.reminder_email` / `reminder_email_at` in Supabase, and the `[reminder]` log lines.

## Server port

- Default `PORT=3000`.
- In development (`NODE_ENV=development` or `STRICT_PORT=true`), the server exits if the port is already in use so the Vite proxy target stays correct. `npm run dev` pre-clears the port automatically; `npm run dev:server` does not.
- Outside development, if the port is in use, the server tries successive ports (up to 20 attempts).

## Docker / Cloud Run

**Deploys:** every push to `main` on GitHub deploys production. A Cloud Build trigger configured in Google Cloud (not in this repo; `cloudbuild.yaml` and `scripts/cloud-build.sh` belong to the manual `npm run cloud:build`) builds the `Dockerfile` image and deploys the `arl-online` Cloud Run service in `us-east1`. The trigger keeps the service's current env vars and Secret Manager bindings: after the 2026-10-08 push of `6625a4a`, the live `/config.js` still carried `SUPABASE_URL`, `SUPABASE_API` and `SITE_URL`, and `/api/inventory` answered 200. So a push is a release: apply any new migration in Supabase first, and check the live site afterwards. To change env vars or secrets, run `npm run cloud:build`, which replaces the whole env list from `.env` (`--set-env-vars`; see `docs/claude-handoff.md` → **Backlog** → **Deploy and tooling**), or edit them in the Cloud Run console (values the next `cloud:build` would wipe).

Production image: multi-stage `Dockerfile` at the repo root.

| Stage | Role |
|-------|------|
| `build` | `npm ci` + `npm run build` (Vite → `dist/`; copies `locales/` + `content/contracts/` for i18n and member agreement imports) |
| `production` | `npm ci --omit=dev`, `node server.js` (copies `server/` for the email, calendar-invite and Slack builders, `src/lib/` for shared server helpers, `src/assets/` for fonts, brand logos and seed images, and `locales/` for server-side SEO copy) |

**Build-time args** (optional fallback — client auth primarily uses runtime `/config.js`):

- `SUPABASE_URL` / `VITE_SUPABASE_URL`
- `SUPABASE_API` / `VITE_SUPABASE_ANON_KEY`
- `SITE_URL` / `VITE_SITE_URL` — production origin for Supabase email-confirmation redirects (recommended for Cloud Run deploys)

**Runtime env** (Cloud Run / container platform):

- `SUPABASE_URL`, `SUPABASE_API` (required — client auth via `/config.js` + inventory storage)
- `SUPABASE_SERVICE_ROLE_KEY` (required — inventory storage; **Cloud Run deploy via `npm run cloud:build` mounts from Secret Manager**, not plain env vars)
- `SITE_URL` (recommended — email confirmation redirects)
- `RESEND_API_KEY` (required for member approval/refusal emails; **Secret Manager on Cloud Run** when set in `.env` during deploy)
- `PORT` (Cloud Run sets this automatically, default `3000` locally)
- `EMAIL_FROM` (optional)
- `EMAIL_REPLY_TO` (optional; passed by `npm run cloud:build` when set in `.env`)
- `ZOOM_ACCOUNT_ID`, `ZOOM_CLIENT_ID` (plain env) + `ZOOM_CLIENT_SECRET` (**Secret Manager** `zoom-client-secret`) — set by `npm run cloud:build` when present in `.env`
- `GA_MEASUREMENT_ID`, `GA_API_SECRET` (optional, plain env; both or neither) — staff bookings' GA event from the server. Add them to the live service with `gcloud run services update arl-online --project=activist-resource-library --region=us-east1 --update-env-vars=GA_MEASUREMENT_ID=G-5VERECD6ZJ,GA_API_SECRET=…` (keeps the other variables), and to `.env` so `npm run cloud:build` (which replaces every variable) keeps them

**Secret Manager (Cloud Run):** Before first `npm run cloud:build` deploy with secrets, create `supabase-service-role-key` and optionally `resend-api-key` secrets and grant the Cloud Run service account `secretAccessor`. One-time `gcloud` commands are documented in the comment block at the top of `scripts/cloud-build.sh`.

**Local build and run:** `npm run docker:build` reads Supabase vars from `.env` and passes them as Docker build args. Override the tag with `IMAGE=region-docker.pkg.dev/project/repo/arl-online:latest npm run docker:build`.

```bash
docker build \
 --build-arg SUPABASE_URL=https://your-project.supabase.co \
 --build-arg SUPABASE_API=your-anon-key \
 --build-arg SITE_URL=https://activistresourcelibrary.com \
 -t arl-online .

docker run --rm -p 8080:8080 \
  -e PORT=8080 \
  -e SUPABASE_URL=https://your-project.supabase.co \
  -e SUPABASE_API=your-anon-key \
  -e SUPABASE_SERVICE_ROLE_KEY=your-service-role-key \
  -e RESEND_API_KEY=re_xxxx \
  arl-online
```

**Cloud Run:** choose **Dockerfile** as the build type; pass build args for Supabase if auth is enabled (or rely on runtime `/config.js`); map runtime env for `SUPABASE_URL`, `SUPABASE_API`, email vars; mount `SUPABASE_SERVICE_ROLE_KEY` and `RESEND_API_KEY` via Secret Manager (see `scripts/cloud-build.sh`).

**www host:** `www.activistresourcelibrary.com` needs its own Cloud Run domain mapping (service `arl-online`, region `us-east1`) and the DNS record Google shows for it (normally `CNAME www → ghs.googlehosted.com.` at Namecheap) so Google issues a certificate. The apex sends HSTS with `includeSubDomains`, so a plain-HTTP DNS redirect would not work for returning visitors. Once requests reach the service, `server.js` 301s them to the apex (sessions, OAuth redirect URLs and canonical URLs all use the apex).

**Persistence:** Inventory and reservations live in Supabase Postgres. Apply `supabase/migrations/001_inventory.sql`, `002_reservation_approval.sql`, `003_lock_down_roles.sql`, `004_inventory_slug.sql`, `005_expertise.sql`, `006_consultation_scheduling.sql`, `007_expertise_copy.sql`, `008_consultation_follow_up.sql`, `009_admin_stats.sql`, `010_item_locations.sql`, `011_item_location_stations.sql`, `012_staff_bookings.sql`, `013_staff_booking_ga_events.sql` and `014_account_email_change.sql` to your project before deploying (009 before the admin Members and Stats code goes live: deleting a member writes `reservations.anonymized_at`; 010 to 014 whenever convenient, though staff bookings made before 012 stay unmarked, before 013 their GA event goes from the browser, tests included, and before 014 an account email change leaves its records under the old address). Then `015_item_owners_and_reminders.sql`, after 014 (re-run it if 014 is applied later); until it is applied items have no owner and no reminders are sent. Then `016_reservation_messages.sql` before deploying the code that uses it; until it is applied booking messages answer 503.

## Google Search Console setup

1. **Verify ownership** — In [Google Search Console](https://search.google.com/search-console), add the property `https://activistresourcelibrary.com` (URL-prefix or domain property).
2. **HTML tag or DNS** — Use the meta-tag verification method (temporary tag in `index.html`) or DNS TXT record via your domain host. Remove the verification meta tag after confirming if you used the HTML method.
3. **Submit sitemap** — After deploy, submit `https://activistresourcelibrary.com/sitemap.xml` under **Sitemaps**. The dynamic sitemap lists static routes plus every inventory item at `/{tag}/{slug}` with `lastmod`.
4. **Check robots.txt** — Confirm `https://activistresourcelibrary.com/robots.txt` allows `/`, `/api/inventory$` and `/api/inventory/by-slug/`, disallows `/api/`, `/admin` and `/account`, and references the sitemap URL. Re-fetch it under **Settings → robots.txt** after a deploy that changes it.
5. **Inspect URLs** — Use **URL inspection** on the homepage and `/howthisworks` to confirm canonical, hreflang (`?lang=en` / `?lang=fr`), and Organization JSON-LD on public pages. On an item page (e.g. a `/books/...` URL from the sitemap), **Test live URL → View tested page** should show the item title in the screenshot and HTML, and **More info → Page resources** should list `/api/inventory/by-slug/...` as loaded, not blocked; the item page should carry exactly one Product and one Organization JSON-LD block. `/admin` should show `noindex` (meta + `X-Robots-Tag`). A made-up path (e.g. `/how-it-works`) or a deleted item's URL should return **404** (Not found), not Soft 404.
6. **Optional analytics** — Set `PLAUSIBLE_DOMAIN=activistresourcelibrary.com` in production env for privacy-friendly traffic data alongside Search Console.
