## What this app does

ARL Online is a small inventory browser with an admin flow:

- **Homepage** — `/` (`HomePage.svelte`) is a short welcome (`home.heading`, `home.intro`, `home.free`), four category links with icons (Expertise, Equipment, Books, Rooms, each with a one-line `home.{tag}_description`), **Meet our experts** (four random mentors, linking to their profiles), the same kind of random picks from the other shelves (**View our equipment** and **Browse our books**, four each; **See our rooms**, two), and two numbered steps at the bottom of the card.
- **Site footer** — every page ends with `SiteFooter.svelte`: the library's name and a one-line blurb, the **Created by** FES / **Run by** Apathy is Boring logos, a **Library** column (the four categories) and a **Help & info** column (How it works, About, Contact us, Privacy policy, Join our Discord), then a copyright line.
- **Inventory** — lists items (title, body, image, tag) loaded from the server. Filter buttons show **Expertise**, **Equipment**, **Books**, or **Rooms**, in `INVENTORY_TAGS` order (a 2×2 grid on phones, one column at ≤360px). Category paths: `/equipment`, `/books`, `/rooms`, `/expertise` (`/` is the homepage, not a category). Non-expertise cards show a real-time **Available**, **Check availability** (no bookable window within 7 days), or **Unavailable** badge (confirmed `reserved` only — pending requests do not mark the card unavailable); **expertise cards hide the badge**. Clicking anywhere on a card or on **Reserve Inventory** / **Request Consultation** updates the browser URL to `/{tag}/{slug}` (Reserve/Request adds `?reserve=1`) while keeping the inventory grid mounted; `ItemDetailPage` renders the item as a modal **overlay** (`<dialog>`) on top of the grid (it is no longer a full-page route). Equipment, books, and rooms use a three-column overlay (image | description | calendar). Expertise uses a compact overlay (small photo, long bio, consultation form). Availability status appears inline in the breadcrumb after the item title (hidden for expertise). The Expertise list shows each expert's short text; the long text appears when that expert is opened. Signed-out users who confirm a reservation/consultation or arrive via `?reserve=1` see a sign-up prompt dialog (Register opens the header auth modal). `?reserve=1` scrolls/highlights the right column for signed-in users. Closing the overlay (X, Escape, backdrop click, or browser Back) returns to the underlying inventory/category path; deep links / refreshes on `/{tag}/{slug}` render the matching category grid with the overlay open on top. Confirming dates (equipment/books/rooms) submits a **pending** reservation via `POST /api/inventory/:id/reservations` (member email derived from JWT on the server), which triggers the optional Slack webhook (awaited for at most 5 s; a Slack failure never fails the request). The member sees a message that AisB will review and email confirmation, and can follow the request (and withdraw it, or cancel an approved booking before its first day) on `/account` (`AccountReservations.svelte`). Reservation create requires a valid Supabase session (`Authorization: Bearer` JWT). Cancelling the auth prompt removes `?reserve=1` via `history.replaceState`. See **Expertise consultations** below for the consultation flow.
- **Header admin** — signed-in `@apathyisboring.com` admins reach `/admin` via the **Admin** link on the `/account` page (not the site header). The admin page shows add-item (including Expertise + optional expert email), **Mentors** (browse expertise items and edit name, expert email, short text, long text, and photo; the public slug stays the same), remove-items, **Pending Reservations** (approve/refuse; expertise rows require a meeting date+time and approving schedules the Zoom consultation), and **Edit Reservations** (delete approved reservations; each row shows the member's email; expertise rows show booked meeting time + Zoom link, and deleting one cancels the Zoom meeting and emails both people; deleting an equipment, book or room booking that hasn't ended emails the member); images are compressed client-side before upload. Approve/refuse call `POST .../approve` or `POST .../refuse` and email the member via Resend. Non-admins who visit `/admin` directly see an access-denied message.
- **Header auth** — optional Supabase email/password login and registration, plus **Log in / Sign up with Google** and **with Discord** buttons above the email form for each OAuth provider enabled in Supabase (see **Auth (Supabase) → OAuth providers**) (Log in / Register in the site header when signed out; **View account** + **Sign out** when signed in — Sign out triggers Kimchi `kimchi.signed_out`). **View account** navigates to `/account`. Sign-up requires reading the member agreement (`content/contracts/{locale}/member-agreement.md`; covers borrowing, the online account, booking and sharing Expertise, and links the privacy policy at `/privacy`) via a lavender **Sign contract** button; agreeing sets a mint checkmark and stores `signed_member_agreement: true` in Supabase `user_metadata` on `signUp`. Register also includes an optional unchecked **email updates** checkbox; the choice is stored as `email_updates_opt_in` in `user_metadata`. **Forgot password?** in the login form emails a Supabase reset link that brings the member back to the page they were on with a **Set a new password** dialog, and `/account` has **Change password** for accounts with an email/password login (see **Auth (Supabase) → Password reset and change**). Mutating API routes validate the Supabase JWT server-side; admin routes also require an `@apathyisboring.com` email.

Admin UI is hidden unless Supabase auth is configured and the user is signed in with an `@apathyisboring.com` email (`isApathyAdmin` in `src/lib/auth.js`).

## Expertise consultations

Use this section when changing the Expertise category, consultation request form, expert scheduling, cancellation, Zoom meetings, related emails/Slack payloads, or migrations `005_expertise.sql` / `006_consultation_scheduling.sql` / `007_expertise_copy.sql` / `008_consultation_follow_up.sql`. Consultations **reuse** the reservations table and `POST /api/inventory/:id/reservations` — they are not a separate booking system.

**Lifecycle:** `pending` (member submitted) → `reserved` (expert or admin set the meeting time; Zoom meeting created) → `cancelled` (member, expert, or admin). Admins can also `refuse` a pending request. A **follow-up** is a new row the expert books from a meeting that has started; it is written straight as `reserved` (Zoom meeting created) with `follow_up_of` pointing at that meeting. There is no `completed` status: a `reserved` row whose meeting ended (`meetingAt` + 60 min) is **held**, and the server and client both derive that with `isConsultationHeld()` in `src/lib/reservation-rules.js`. A held meeting can't be cancelled, and admin deletes treat it as a record only (no Zoom delete, no emails).

**Who is the expert:** the signed-in user whose **confirmed** Supabase email matches the item's `expert_email` (case-insensitive, compared in JS). Experts use the normal `/account` page — no separate role or table. Items without `expert_email` can only be scheduled by admins.

### Member flow

1. Filter **Expertise** (`/expertise`). The list uses the same cards and grid as the other categories (3 cards per row from 900px, one column on small screens). Each card shows the photo in the standard image frame, the name, and the **short text**, with no availability badge. **Request Consultation** opens `/{tag}/{slug}?reserve=1`.
2. Opening an expert shows the **long text** plus `ConsultationRequestForm.svelte` in a narrow overlay (no availability badge, no three-column calendar layout).
3. Member submits free-text **time slots** + **summary** (auth-gated like Reserve). Client posts `{ timeSlots, summary }`.
4. Server stores a `pending` reservation with `start_date`/`end_date` = submission date (`toDateKey(new Date())`), plus `time_slots` / `request_summary`. **No date collision check** (multiple members may request the same expert). A member can have only **one open request per expert**: if they already have a pending or upcoming (not yet held) consultation on that item, `addReservation` returns 409 `consultation_already_open` inside the item lock. Each account can also create at most **10 reservations or consultation requests per 24 hours** (429 `daily_request_limit`). Both errors show in EN/FR in the form (and the 429 in the calendar). So do the route's other two 429s, which carry codes as well: the 5-pending cap (`pending_request_limit`) and the IP limiter (`reservation_rate_limited`).
5. Slack webhook fires. Member gets “request received” email; **expert gets “new consultation request” email** linking to `/account`. Kimchi shows `kimchi.consultation_sent`. The form says, above and under **Submit**, that the request and the member's account email go to the named expert and to the Apathy is Boring team (`consultation.intro`, `consultation.sharing_note`).
6. `/account` → **Your consultation requests** (`AccountConsultations.svelte`) lists active requests only: status, slots, summary, expert email, and — once scheduled — meeting time, **Join Zoom** link, and passcode. **Cancel** on pending or upcoming scheduled requests. Cancelled, declined, and finished meetings (60 minutes after the start) stay behind a **Past consultations** button on that list. A follow-up the expert booked shows a **Follow-up** badge (`account_consultations.follow_up_badge`) and the expert's optional note under **Follow-up note**; the member can cancel it like any scheduled meeting. Members can't book follow-ups themselves; they can request a new consultation once nothing is open with that expert. After **Cancel**, Kimchi says `kimchi.consultation_withdrawn` (pending) or `consultation_cancelled_member` (scheduled), "{title} has been told", only when the response has `otherPartyEmailed: true` (a mentor may have no email); otherwise the `_plain` version. On load Kimchi says at most one thing about the lists, in the order meeting starting soon (B6) > closed by the other side (B4) > new requests for an expert (B5) > a request waiting a week or more (C8, with a **Contact us** link to `/about#contact`); see `docs/automated-notifications.md`. A scheduled meeting shows a **Starts in N min** chip from 15 minutes before its start and **Happening now** until it ends, and rows the other side cancelled or declined since this browser's last visit show for that visit under **Changed since your last visit**.

### Share Expertise

Every signed-in account can open **Share Expertise** from a button on the account panel (`AccountShareExpertise.svelte`). The form stays closed until that button is clicked, then appears above the consultation lists. Closing it keeps any unsaved edits.

1. A **confirmed** email is required. Unconfirmed accounts see a prompt to confirm before the form is shown (`GET /api/account/mentor-profile` returns `{ profile: null, emailConfirmed: false }`).
2. The member publishes **one** mentor profile: name (max 120), photo, short text, and long text. `POST /api/account/mentor-profile` creates an expertise item and sets `expert_email` to the JWT email. The client cannot choose a different address. A second create returns **409** with the existing profile.
3. The profile is a normal expertise item, so it appears on the Expertise list immediately. The slug is generated once and stays fixed when the profile is edited.
4. **Edit** is available when that item's `expert_email` matches the account email (case-insensitive). `PATCH /api/account/mentor-profile` updates name, short text, long text, and an optional new photo. It does not change `expert_email` or the slug. If several expertise items share the email, the earliest one is the profile they edit, and create stays blocked. An admin-created mentor with that email opens in the same editor.
5. Photos are capped at 2,000,000 data-URL characters (413 `image_too_large`) and must be an uploaded JPEG, PNG, WebP or GIF data URL (400 `image_invalid`; unlike the admin routes, `/assets/inventory/` seed paths are refused); the client shows both in EN/FR. The routes use a **3mb** JSON limit. The profile `image` comes back as a `/media/items/...` URL, and sending that URL back on `PATCH` means "photo unchanged". Creates and updates are rate-limited (10 per 15 minutes) and serialized with an in-process per-email lock (single Cloud Run instance). Kimchi: `kimchi.mentor_profile_published` / `kimchi.mentor_profile_updated`.
6. Profiles go live without review, so each successful publish, and each edit that changes something, posts a **Slack staff alert** (`notifySlackAlert()`, status `mentor_profile_published` / `mentor_profile_updated`; `request_summary` names the profile, the account email, a rename and the changed fields, and links the page). The route waits for it (at most 5 s) and a Slack failure never fails the save. No email is sent.

### Expert flow

1. Logs in (or registers) with the `expert_email` address and opens `/account` → **Consultation requests for you** (only shown when they have any). The list shows pending and upcoming meetings. Cancelled, declined, and finished meetings open from **Past consultations** on that section.
2. Each pending row shows member email, time slots, summary, and a **Meeting date and time** field: a visible native `datetime-local` input (`MeetingTimePicker.svelte`). Tapping it opens the system date-time picker on iOS and Android; desktop browsers show editable date and time segments. The value is read as local time by `parseMeetingTimeInput()` and sent as ISO. Then **Schedule meeting**. No time shows `meeting_time_required`; a time in the past shows `meeting_time_past` (iOS doesn't enforce `min` in its picker). Both appear under the field, which gets focus and `aria-invalid`.
3. Schedule → `POST /api/consultations/:reservationId/schedule { meetingAt }` → Zoom meeting created → `reserved` with `meeting_at` + `zoom_*` → both get “scheduled” emails with Zoom link and `.ics` invite. Kimchi `kimchi.consultation_scheduled` (or `kimchi.consultation_scheduled_plain`, without "invitations are on their way", when the response has `emailSent === false`); a hidden status line announces it and focus moves to the row's title.
4. **Cancel** (pending or scheduled) → `POST /api/consultations/:reservationId/cancel` → `cancelled` + `cancelled_by: 'expert'` → Zoom meeting deleted → both emailed. Kimchi `kimchi.consultation_closed_expert` (pending) / `consultation_cancelled_expert` (scheduled), or the `_plain` version when the response says the email didn't go out (`emailSent` or `otherPartyEmailed` false); a hidden status line announces it and focus moves to the **Past consultations** toggle. A held meeting returns 400 `consultation_already_held` (`account_consultations.already_held`); the UI already hides **Cancel** once a meeting is finished.
5. **Book a follow-up** (agreed during the call): on a `reserved` meeting whose start time has passed, **Book a follow-up** (`account_consultations.follow_up_open`) opens a panel with a `MeetingTimePicker` and an optional note (max 1000, `FOLLOW_UP_NOTE_MAX` in `src/lib/expertise-fields.js`). **Book follow-up** → confirm → `POST /api/consultations/:reservationId/follow-up { meetingAt, note }` → `bookFollowUpConsultation` (item lock) creates the Zoom meeting and inserts a new `reserved` row for the same member (`follow_up_of` = the source id, `request_summary` = the note, no `time_slots`, `start_date` = today in Montréal) → both get the scheduled emails worded as a follow-up, and staff get a Slack alert. The new row is added to the list, and Kimchi says `kimchi.follow_up_booked` (`_plain` when `emailSent === false`); focus moves to the new meeting's title. The button shows only on the member's latest started meeting with that expert and only while nothing else is open between them (no pending request, no upcoming meeting; `canBookFollowUp()` in `src/lib/reservation-rules.js`, shared with `/admin`), so a meeting that just ended sits under **Past consultations** with the button; during the call (the first 60 minutes) it is still in the active list. Same time checks as scheduling (`meeting_time_required` / `meeting_time_past`).

### Admin flow

1. Add expertise items via Add Item → **Expertise**; optional **Expert email** (`expertEmail` → `inventory_items.expert_email`; admin-only, stripped from public API), required **Short text** (`body`, max 180, shown on the list) and **Long text** (`longBody` → `inventory_items.long_body`, max 4000, shown when the expert is opened). Apply `007_expertise_copy.sql` before saving long text. Items saved before separate fields exist keep working: the first paragraph of `body` is the list text, and the rest (after a blank line) is the overlay text, until `longBody` is set.
2. **Mentors** lists expertise items (photo, name, expert email, short text). **Edit** saves name, expert email (blank clears it), short text, long text, and an optional new photo via `PATCH /api/inventory/:id`. The slug is not regenerated. Older bios without `longBody` open with the blank-line split already filled in.
3. Pending list shows requested date, time slots, summary, and the same **Meeting date and time** field (`MeetingTimePicker`, required `meetingAt`). No time shows `admin.meeting_time_required` and a past time `admin.meeting_time_past`, under the field, before the confirm; the field gets focus. On phones the expertise row stacks (it also carries `consultation-row`). **Approve = schedule** (same `runScheduleConsultation` as the expert path: Zoom + both emails). Refuse sends the member the consultation decline email. A request for a mentor with no expert email carries a **No mentor email** pill (`admin.no_mentor_email`, also on that mentor's scheduled, not-held rows in Edit Reservations), and its approve, follow-up, delete and remove confirms use the `admin.*_no_expert_email` versions: only the member is invited, so staff send the mentor the Zoom link. Kimchi says "scheduled" (`kimchi.consultation_scheduled`, `_no_expert_email`, `_no_expert_email_no_zoom` or `_plain`) and, on refuse, `kimchi.consultation_refused` (`_plain` when `emailSent === false`).
4. Edit Reservations shows the meeting time, Zoom link and member email. **Delete** of an active consultation (or deleting the expertise item) deletes the Zoom meeting and emails both as an admin cancellation; its confirm names the member (`admin.delete_consultation_confirm`). Held meetings are labeled **Completed** (`account_consultations.status_completed`); deleting one only removes the record, and its confirm says nobody is notified (`admin.delete_held_consultation_confirm`). Follow-ups carry a **Follow-up** badge. A started meeting that qualifies (same `canBookFollowUp()` rule as `/account`, computed from the item's reservations) gets **Book a follow-up**: the same panel as the expert's (`admin.follow_up_intro`, `MeetingTimePicker`, optional note) → `admin.follow_up_confirm` → `POST /api/consultations/:id/follow-up`; for admins the response also carries the full `item`, which replaces the item's reservations like approve does. Expertise rows here carry `consultation-row`, so they stack on phones.
5. **Remove Item** on an expertise item with any consultation rows warns that its consultation records will be permanently deleted (they cascade with the item) and gives the count (`admin.remove_expertise_confirm`). Pending and upcoming consultations are still cancelled with emails; held ones are deleted without notice.

### Zoom (`src/lib/zoom.js`)

| Concern | Behavior |
|---------|----------|
| Auth | Server-to-Server OAuth (`ZOOM_ACCOUNT_ID`, `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`); token cached until ~1 min before expiry |
| Host | `ZOOM_HOST_USER` (default `me` = the app owner's licensed Zoom user). Members/experts don't need Zoom accounts |
| Meeting | Scheduled (type 2), 60 min, `America/Toronto`, `join_before_host: true`, `jbh_time: 0`, `waiting_room: false`, passcode auto-generated by Zoom. Topic `ARL consultation: {title}` (summary is **not** sent to Zoom) |
| Screen share for all | Host-user setting, not per-meeting. Attempted once per process via `PATCH /users/{host}/settings` — requires `user:update:settings:admin` scope; otherwise set **Who can share = All Participants** in the Zoom web portal |
| Create failure | Inside the item lock, before the DB write → 502, reservation stays `pending` (a follow-up saves nothing). DB error after create → meeting deleted (also for a failed follow-up insert). The update is guarded with `.eq('status', 'pending').select('id')`; if no row changed (request no longer pending), the meeting is deleted and the route returns 400 with no emails |
| Delete | On cancel / admin delete of a consultation that is not yet held; 404 treated as success; other errors logged (cancellation still succeeds) |
| Not configured | Schedules without a meeting; emails say a link will follow |
| Invitations | Zoom's API does not email anyone — invitations are our Resend emails + `.ics` (`METHOD:REQUEST`, cancel sends `METHOD:CANCEL` with the same UID) |
| Diagnostics | `npm run zoom:check` (token, scopes, host user, share settings) |

### API / sanitization notes

| Concern | Behavior |
|---------|----------|
| Create body | Expertise: `{ timeSlots, summary }`. Other tags: `{ startDate, endDate }` |
| `GET /api/account/consultations` | `{ asMember, asExpert }`; `asExpert` only for confirmed emails. Members see `expertEmail`; experts see `memberEmail`; Zoom link/passcode only while `reserved` |
| Mentor profile | `GET/POST/PATCH /api/account/mentor-profile`. One expertise item per confirmed account email. Response includes `expertEmail` because it is that account's address. Public inventory routes still omit it |
| Schedule | `POST /api/consultations/:id/schedule { meetingAt }` — expert or admin; meeting must not be >5 min in the past; 403 for the member; 404 for unrelated users |
| Cancel | `POST /api/consultations/:id/cancel` — member, expert, or admin; only `pending`/`reserved`, and not a held meeting (400 `consultation_already_held`). Returns `{ consultation, emailSent, otherPartyEmailed }`: `otherPartyEmailed` is `emailSent` and the other side has an address on file (the trimmed `item.expertEmail` when a member cancels, the trimmed `reservation.userEmail` when the expert does, both when an admin does). Only the boolean is returned, never an address |
| Follow-up | `POST /api/consultations/:id/follow-up { meetingAt, note? }` — expert or admin (403 for the member, 404 for unrelated users). Source must be `reserved` with `meetingAt` ≤ now (else 400 `follow_up_not_available`); the member must have nothing else open on that item (else 409 `follow_up_already_open`); note ≤ 1000; same `meetingAt` rule as schedule. 201 `{ consultation, emailSent }`, plus the full `item` (admin shape) when the caller is an admin; 502 if Zoom fails (nothing saved). Uses `consultationActionLimiter`, not the reservation-create limiters |
| Admin approve | Expertise requires `{ meetingAt }`; routes into the same schedule logic |
| Public responses | Whitelisted reservation fields only (`id`, `startDate`, `endDate`, `status`); no `expertEmail` or `followUpOf`. Expertise items include public `longBody` (null on other tags) |
| Item `image` | Every response that carries an item (public, admin, mentor profile) sends uploaded photos as `/media/items/{id}/{hash}.{ext}`, never the stored data URL (`withPublicItemImage` / `publicItemImageUrl` in `src/lib/item-media.js`) |
| Collision | Skipped for `tag === 'expertise'` in `addReservation` (`patchReservation` rejects expertise rows) |
| Pending cap | Still max 5 pending reservations per user (all tags); cancelled requests free a slot. 429 `{ error, code: 'pending_request_limit' }` (`calendar.pending_limit`); the 30/15 min IP limiter's 429 carries `code: 'reservation_rate_limited'` (`calendar.rate_limited`) |
| Daily cap | Max 10 successful creates per account per 24 hours, all tags (`reservationAccountLimiter`, keyed by Supabase user id, after `requireAuth`; the 30/15 min IP limiter still runs first). 429 `{ error, code: 'daily_request_limit' }`. Only saved creates count: the limiter (explicit `MemoryStore`) counts every request it lets through, and `countSavedReservationCreates()` hands the hit back once the route has finished without saving (`res.locals.reservationSaved`). A client that disconnects while the route awaits Slack and the emails still uses one. In-memory, so it relies on the single Cloud Run instance and resets on deploy. It stops request → cancel loops from emailing a mentor and posting to Slack over and over |
| One open request per expert | A member with a `pending`, or `reserved` and not yet held, consultation on the same item gets 409 `{ error, code: 'consultation_already_open' }` (checked in `addReservation`, inside the item lock). Held, cancelled and refused rows don't block a new request |
| Held | `isConsultationHeld(r)` (`reservation-rules.js`): `reserved`, `meetingAt` set, and `meetingAt` + 60 min ≤ now. Admin reservation `DELETE` and item `DELETE` skip `handleConsultationCancelled` for held rows (no Zoom delete, no emails); `cancelConsultation` returns `alreadyHeld` |
| Concurrency | Schedule/cancel run in the per-item in-process lock. Mentor profile create/update uses a per-email lock (single Cloud Run instance assumption) |

### Emails & Slack

| Trigger | What fires |
|---------|------------|
| Consultation create | Member “request received” + expert “new consultation request” (`sendConsultationRequestEmails`) + Slack |
| Schedule (expert or admin) | Member “Consultation confirmed” + expert “Consultation scheduled”, both with Zoom link + `.ics` (`buildConsultationScheduledEmailPayloads`) |
| Cancel / admin delete | Both get “Consultation cancelled” naming who cancelled (`buildConsultationCancelledEmailPayloads`); `.ics` CANCEL if it was scheduled. Not for held meetings: cancel is refused and admin deletes send nothing |
| Admin refuse | Member decline email (`buildConsultationDecisionEmailPayload`) |
| Follow-up booked (expert) | The same scheduled emails, worded “Follow-up consultation confirmed / scheduled” with the note as **Follow-up note** in both; `.ics` summary “Follow-up consultation: {title}”. Plus a Slack staff alert (`notifySlackAlert`, status `consultation_follow_up`, the new reservation's id and dates) |
| Mentor profile publish / edit | Slack staff alert only (`notifySlackAlert`, status `mentor_profile_published` / `mentor_profile_updated`); an edit that changed nothing sends none |
| Placeholder | `CONSULTATION_DATA_FORM_URL` in `server.js` — replace before launch |

Each route waits for its emails (and, on create, follow-up and mentor-profile saves, the Slack post) before it responds, and adds `emailSent` to its JSON. A failed send is logged and never fails the saved action. Every consultation email sets `Reply-To` to `EMAIL_REPLY_TO`.

Details: `docs/automated-emails.md`, `docs/automated-webhooks.md`, `docs/automated-notifications.md`.

## Architecture overview

```
┌─────────────────────────────────────────────────────────┐
│  Browser (Svelte 5 SPA, built by Vite → dist/)          │
│  src/App.svelte + components + lib                      │
└──────────────────────────┬──────────────────────────────┘
                           │ fetch /api/*
┌──────────────────────────▼──────────────────────────────┐
│  Express server (server.js)                               │
│  - REST API                                               │
│  - Serves dist/ (production UI)                           │
│  - Serves src/assets/fonts and brand at /assets/fonts, /assets/brand │
│  - Persists inventory + reservations to Supabase (Postgres) │
│  - Sends email via Resend                                 │
└─────────────────────────────────────────────────────────┘
```

**Local dev:** `npm run dev` starts both required processes so the Vite URL can load API data and server-owned assets.

**Local dev uses the production database.** The local `.env` points at the production Supabase project and has live Zoom, Resend, and Slack credentials, so `npm run dev` reads and writes real data. Requesting, scheduling, or cancelling locally creates real Zoom meetings, sends real emails, and posts to Slack. Browse read-only, and test write paths against a mocked Supabase client (or a separate dev project) unless the user approves a live test.

| Process | Command | URL | Role |
|---------|---------|-----|------|
| Vite dev server | `npm run dev` (or `npm run dev:client`) | http://localhost:5173 | Svelte UI with HMR; proxies `/api`, `/media`, `/assets/brand`, `/assets/fonts`, `/assets/inventory`, `/robots.txt`, and `/sitemap.xml` to Express |
| Express API/static server | `npm run dev` (or `npm run dev:server`) | http://localhost:3000 | Serves API routes plus static fonts, brand logos, and inventory seed assets |

In development, Express uses a strict port so Vite's proxy cannot silently point at the wrong server. `npm run dev` (via `scripts/dev.js`) automatically frees the API port before starting — manual intervention is rarely needed. For `npm run dev:server` alone, if port 3000 is already in use you must stop the old server or set `PORT`.

**Production / preview:** `npm start` rebuilds `dist/` before starting Express. Use `npm run serve` only when you intentionally want to serve the existing built files without rebuilding.

## Frontend (Svelte 5)

### Entry and root

- `index.html` loads `/src/main.js` and includes the Google Analytics tag (`G-5VERECD6ZJ`) immediately after `<head>`. After `<div id="app"></div>` sits the **boot card**: a sibling `<div class="boot" role="status">` with sleeping Kimchi (`/content/kimchi-sleep.jpg`, which Vite inlines as a `data:` URI because Express doesn't serve `/content`), three Mint hopping dots and a visually hidden bilingual `Loading… / Chargement…`. It is invisible for 450ms, then fades in, so warm loads never see it; `#app:not(:empty) + .boot { display: none }` hides it the frame Svelte mounts, so `main.js` needs no change. Its CSS is a small inline `<style>` in `<head>` (hex values only), the one deliberate exception to "all CSS in `app.css`": the card must be styled before the bundle's CSS exists, also in dev. It adds no script, so the CSP script hashes are unchanged.
- `main.js` uses Svelte 5 `mount()` when `#app` exists and imports global `app.css`.
- `App.svelte` holds top-level state: `items`, `loading`, `loadError`. It loads inventory on mount (also on the homepage, so the first category click is instant), routes between the homepage (`/`, `HomePage`, imported eagerly because it is the main landing page), inventory (`/equipment`, `/books`, `/rooms`, `/expertise`), **How it works** (`/howthisworks`), **About** (`/about`), **Privacy** (`/privacy`), **Account** (`/account`), and admin (`/admin`) via `src/lib/router.js`. On item routes (`/{tag}/{slug}` e.g. `/equipment/megaphone` or `/expertise/some-expert`) it renders the inventory grid **and** the lazy-loaded `ItemDetailPage` overlay concurrently (the grid stays mounted underneath; `InventoryPanel` filters to the item's tag), so deep links show the item overlay on top of the right category grid. Any other path (`!isKnownAppPath`) renders a small **not-found view** (`not_found.*`: heading, one sentence, link back to the library) in `<main id="main-content">`. It wires a skip link (`site.skip_to_content` → `#main-content`), client-side SEO tags via `src/lib/seo.js` (`$effect` on route + locale; per-item Product JSON-LD on detail routes; on the item URL the page was loaded at it leaves the server-injected tags alone until `ItemDetailPage` reports the item, and after a load error, while a client-side navigation to an item gets the route defaults until the item arrives; item results only count for the path they were loaded for (`itemDetailSeoPath`), since the overlay mounts asynchronously and a slow fetch can finish after the route moved on; a missing item or unknown path gets `getNotFoundSeoConfig` — "Page not found" title + `noindex, nofollow`, no JSON-LD), Google Analytics + optional Plausible SPA pageviews on route change when each script is present, a lemon **PSA banner** (localized hyperlink above the header), the site header (logo, which goes home in-app through `goHome` → `navigateToPage('/')` instead of a full reload; `SiteNav`; `LocaleSwitcher`; `HeaderAuth`), lazy-loaded admin / how-it-works / about / privacy / account / item-detail pages, the add-item modal (lazy, mounted only on `/admin`), the site footer (`SiteFooter`, the last child of `.app`, on every page including `/admin` and the not-found view; it carries the FES / AisB credit), and the `KimchiNotification` chat widget. When the route leaves an item path (overlay closed by X, Escape, backdrop, browser Back or a breadcrumb), an `$effect` moves focus to that item's card link (`.inventory-card__title-link`, or a homepage `.home-expert` or `.home-item` link, whose `pathname` is the item path) or, if the card isn't in the grid, to `#main-content h1` (given `tabindex="-1"`). It only acts when focus fell to `<body>`, never on the initial load or other navigation, skips the scroll when the target is already on screen above the bottom `scroll-padding`, and polls briefly (50 ms timer, up to 1 s) for lazy pages such as Back to `/account`. **Lazy chunks across deploys:** each lazy page is a separate content-hashed chunk, and a tab opened before a deploy still asks for the old file names, which the server answers with a plain-text 404. Every `{#await import()}` has a `{:pending}` branch that renders `RouteProgress.svelte` (the five lazy pages and the item overlay) and a `{:catch}` that renders `PageLoadError.svelte` (`page_load_error.*`, EN/FR): on mount it reloads the page once (skipped when `navigator.onLine === false`; a `sessionStorage` timestamp, `arl-chunk-reload-at`, allows one auto-reload per 60 s so a chunk that stays missing cannot loop), otherwise it shows the message and a **Reload the page** button, in `<main id="main-content">` for pages or floating at the top of the viewport for the item overlay. The `AddItemModal` catch renders nothing (AdminPage's own catch covers `/admin`). There is deliberately no global `vite:preloadError` reload, so a failed background fetch never reloads the page on its own. **Item overlay warm-up:** after the inventory loads, `App.svelte` imports `ItemDetailPage` in `requestIdleCallback` (3 s timeout; 1 s `setTimeout` where unsupported), so the first card click opens the overlay without a network round trip and a tab left open across a deploy already holds the chunk; a failed warm-up is silent. ### Auth (Supabase)

- **OAuth providers (Google, Discord):** buttons appear automatically for each provider enabled in Supabase → **Authentication** → **Sign In / Providers** (`initAuth` → `loadOAuthProviders()` reads `external.google` / `external.discord` from `/auth/v1/settings`); no env vars or deploy needed. Setup per provider: create an OAuth app (Google Cloud Console → OAuth client, type *Web application*; Discord Developer Portal → OAuth2), set its redirect URI to `https://<project-ref>.supabase.co/auth/v1/callback`, paste the client ID + secret into the Supabase provider. `signInWithOAuthProvider` returns the visitor to the page they started on (`origin + pathname + search`, so `?reserve=1` survives); that URL must match Supabase **Redirect URLs** (add `https://activistresourcelibrary.com/**` and `http://localhost:5173/**`), otherwise Supabase falls back to the Site URL. Supabase links an OAuth identity to an existing account with the same verified email. Discord accounts without a verified email fail at Supabase; the redirect error opens the login modal with `auth.oauth_no_email` (other redirect errors show `auth.oauth_failed` + the Supabase message).
- **Member agreement for OAuth accounts:** OAuth sign-up skips the register form. `userNeedsMemberAgreement(user)` is true when `user_metadata.signed_member_agreement` is not `true` **and** `app_metadata.provider` is not `email` (legacy email accounts that predate the flag are never prompted). If the agreement was signed in the register form before the OAuth click, the choice is stashed in `sessionStorage` (`arl-pending-oauth-signup`, 30 min) and applied with `supabase.auth.updateUser` on return; otherwise `CompleteSignupModal` asks for it. Like the email flow, this is client-side only; the server does not check the flag.
- **Password reset and change** (client-only; Supabase Auth does the work, no Express route):
  - **Request:** login dialog → **Forgot password?** → reset view → `requestPasswordReset(email)` → `supabase.auth.resetPasswordForEmail(email, { redirectTo })`. `redirectTo` is the current page (`window.location` origin + path + query) without `?reserve`, with an item path `/{tag}/{slug}` swapped for its category (the overlay would otherwise open over the new-password dialog), plus `?password_reset=1`. Like OAuth, it must match Supabase **Redirect URLs** — keep `https://activistresourcelibrary.com/**` (and `http://localhost:5173/**`), otherwise Supabase falls back to the Site URL without the flag. The dialog always shows the neutral `auth.reset_sent`, so it never says whether an address has an account; only rate limits, a malformed address and network/server failures show an error.
  - **Landing:** Supabase's verify link redirects to `redirectTo#access_token=…&type=recovery` (implicit flow). supabase-js saves that session and fires `PASSWORD_RECOVERY` on a timer that can run before `initAuth` subscribes, so `supabase.js` notes `type=recovery` synchronously and `passwordPrompt` starts as `'recovery'`; the `PASSWORD_RECOVERY` listener covers late events. supabase-js also relays that event (and the new session) to every other open tab of the site, so the listener only acts when `authCallbackRecovery` is true: the tab where the member asked for the link (often still showing the reset view) signs in but does not open a second dialog. `initAuth` awaits `supabase.auth.initialize()`: if the tokens are rejected it clears the prompt (a stored session, possibly another account, stays signed in and is not offered a new password) and reports `passwordResetLinkFailed`. `SetPasswordModal` then asks for the new password → `updateUser({ password })`. Staff-sent recovery links from the dashboard (no flag) open the same dialog.
  - **Expired or used link:** Supabase redirects with `#error=access_denied&error_code=otp_expired&error_description=…`. With the `password_reset` flag, `HeaderAuth` opens the reset view with `auth.reset_link_expired` (“This reset link has expired or was already used. Request a new one.”) instead of the generic redirect error. Mail scanners that open links ahead of the member can use up the one-time link and cause this.
  - **Change password:** `/account` shows **Change password** only when `userHasPasswordLogin(user)` (an `email` entry in `app_metadata.providers` or `user.identities`); it opens the same dialog in `'change'` mode. If **Secure password change** is on (Supabase → Authentication → Providers → Email), a session older than 24 h gets `reauthentication_needed` → `auth.password_reauth_needed` (log out and back in). Supabase's own minimum length / leaked-password check returns `weak_password` → `auth.password_weak`; keep the dashboard minimum at 8 or lower, or raise `PASSWORD_MIN_LENGTH` and the `auth.password_min_length` / `auth.password_hint` copy with it.
  - **The email:** Supabase sends it, not Resend. Copy is the **Reset Password** template (Authentication → **Email Templates**; one English template per project; it must keep `{{ .ConfirmationURL }}`). Supabase's built-in sender is for testing: it allows only a few emails per hour for the whole project and delivers only to addresses on the Supabase organization's team (others fail with `email_address_not_authorized`, shown as `auth.reset_send_failed`); set **custom SMTP** (Authentication → **SMTP Settings**, e.g. Resend's SMTP with the verified `activistresourcelibrary.com` domain) so reset and confirmation emails arrive. Supabase also rate-limits reset requests per address (about one per minute), which shows as `auth.rate_limited`.
  - **Stacking:** `CompleteSignupModal` waits while `$passwordPrompt` is set, so a reset link that signs in an OAuth account without the agreement shows the password dialog first, then the agreement.
- Browser client: `@supabase/supabase-js`. **Server:** `requireAuth` middleware validates `Authorization: Bearer <token>` via `getSupabaseAdmin().auth.getUser(token)`; `requireAdmin` requires `@apathyisboring.com` email **and** a confirmed email (`email_confirmed_at` or `confirmed_at` on the Supabase user). **Confirm email MUST stay enabled** in Supabase Auth → Providers → Email so unconfirmed accounts cannot pass `requireAdmin`. Applied to reservation create (auth only) and all inventory admin / reservation mutation routes (auth + admin).
- Production loads **`GET /config.js`** before the SPA bundle (`index.html`); Express injects public Supabase URL, anon key, and `SITE_URL` from runtime env. Vite dev proxies `/config.js` to Express; local dev still works via `.env` when the server is not running.
- `vite.config.js` sets `envPrefix: ['VITE_', 'SITE_']` so only `VITE_*` and `SITE_*` keys are exposed to the client build (prevents accidental service-role leak). Supabase public creds come from `/config.js` at runtime or `VITE_SUPABASE_*` in `.env`.
- Enable **Email** provider in the Supabase dashboard. If email confirmation is on, registration shows a “check your email” message and the user logs in after confirming. The page the confirmation link opens (`#type=signup` with a session, `authCallbackSignupConfirmed`) gets Kimchi's `kimchi.email_confirmed` instead of `logged_in`.
- Set **`SITE_URL`** to the public production origin (no trailing slash) for production Docker/Cloud builds so confirmation emails redirect there instead of localhost. ## Backend (Express)

Single file: `server.js`. The first middleware 301s `www.<host>` (for the `SITE_URL` host and `PRODUCTION_SITE_ORIGIN`'s host) to the same path and query on the apex; other hosts (localhost, `*.run.app`) pass through. Uses `helmet` for security headers, `compression` right after it (Brotli/gzip for HTML, JSON, JS and CSS; Cloud Run's front end does not compress, and images/WOFF2 are skipped by type), `app.set('trust proxy', 1)` for correct rate limiting behind Cloud Run, and admin audit logging (`[admin-audit]` console lines on every admin mutation).

**Content Security Policy** — `script-src` has **no `'unsafe-inline'`**. At startup, `extractInlineScriptHashes()` scans the inline executable `<script>` blocks in `dist/index.html` (currently only the Google Analytics gtag bootstrap) and adds a `'sha256-…'` hash for each to `script-src`; the per-request SEO injection only adds JSON-LD data blocks or external scripts, so the same hashes cover every HTML response. To add another inline script, put it in `index.html` and rebuild — the hash list refreshes on server start (restart after `npm run build`). External script sources: `'self'`, `https://*.googletagmanager.com`, and `https://plausible.io` when `PLAUSIBLE_DOMAIN` is set. `connect-src` includes `SUPABASE_URL`, GA collection hosts, and optional Plausible; `img-src` allows `'self'` (which covers `/media/items/...` photos), `data:` (Vite-inlined images; legacy item data URLs) plus GA beacon hosts; `style-src` still allows `'unsafe-inline'` (Svelte inline styles); `frame-ancestors 'none'`.

**Dependency hygiene** — `package.json` `overrides` pins `qs` to `^6.16.0` because Express 4.x still declares `~6.15.x`, which has open advisories. Run `npm audit --omit=dev` before deploying; it must report 0 vulnerabilities. Remove the override once Express 4 (or a move to Express 5) ships a patched range.

### Static assets

- `GET /config.js` — runtime public client config (`window.__ARL_ENV__`: `SUPABASE_URL`, `SUPABASE_API`, `SITE_URL`); `Cache-Control: no-store`.
- `GET /assets/*.js|css`, `/robots.txt`, `/favicon.ico`, `/favicon-16x16.png`, `/favicon-32x32.png`, `/apple-touch-icon.png` from `dist/` — `express.static` with **`index: false, redirect: false`**, so it serves only real files (hashed JS/CSS, `robots.txt`, the icons copied from `public/`). It never serves `index.html` for `/` and never 301-redirects `/about` → `/about/`. Files directly in `dist/assets/` (Vite's content-hashed output) get `Cache-Control: public, max-age=31536000, immutable`; other dist files (`robots.txt`, the icons, the `public/assets/fonts` copies) get `public, max-age=3600`; a direct `/index.html` gets `no-cache`.
- `/assets/*` (anything the asset statics did not serve, e.g. a chunk from an earlier deploy) — `404` `text/plain` `Not found.`, never the SPA shell.
- `GET /media/items/:id/:file` — uploaded photos (stored as data URLs in `inventory_items.image`). Outside `/api/` so crawlers and link previews can fetch og:image (`robots.txt` blocks `/api/` apart from the two public inventory reads). Loads only that item's `image`; 404 (`text/plain`) when the item is missing or the image is not a JPEG/PNG/WebP/GIF data URL (seed paths, SVG). When `:file` is the current `{hash}.{ext}` it sends the decoded bytes with that `Content-Type`, `Cache-Control: public, max-age=31536000, immutable` and `Cross-Origin-Resource-Policy: cross-origin`; otherwise `302` to the current URL with `Cache-Control: no-cache`. Other `/media/*` paths 404.
- `GET /api/*` (unmatched) — JSON `404 { error: 'Not found.' }` (`app.all('/api/*')` before the catch-all), so typo'd or removed API paths do not return the SPA shell as HTML 200.
- `GET *` catch-all — every HTML route (`/`, `/equipment`, `/about`, `/privacy`, `/howthisworks`, `/{tag}/{slug}`, `/admin`, `/account`, trailing-slash variants) is served from the in-memory `dist/index.html` template with per-request SEO injection via `seo-server.js` (single title/description/OG/Twitter set, canonical without trailing slash, hreflang, `<html lang>` for the resolved locale, Organization/FAQ/Product JSON-LD). `/admin` and `/account` also get `X-Robots-Tag: noindex, nofollow` and no JSON-LD. **404s:** a path that is not a known app path (`isKnownAppPath` in `src/lib/item-routes.js`, e.g. `/how-it-works`, `/Equipment`, `/fr`) and a `/{tag}/{slug}` whose slug does not exist get status **404** with the same SPA shell, a `noindex, nofollow` robots meta, the localized `seo.not_found_title` and no JSON-LD; the client then shows its not-found view (or the overlay's **Item not found**). A failed item lookup (Supabase error) stays 200. Sent with `Cache-Control: no-cache`, because the shell names the current hashed bundles. On `/{tag}/{slug}` routes the shell also gets `<link rel="modulepreload" crossorigin href="/assets/ItemDetailPage-[hash].js">`, so a deep link fetches the overlay chunk alongside the entry instead of after it runs. `server.js` finds that file once at startup (`findItemDetailChunkPreload`, matching Vite's default `[name]-[hash].js` name in `dist/assets`); with no match the hint is left out.
- `GET /robots.txt` — static file from `dist/` (copied from `public/` at build). Allows `/`, `/api/inventory` (exact, via `$`) and `/api/inventory/by-slug/`; disallows `/api/`, `/admin`, `/account`. Google applies the longest matching rule, so the rest of `/api/` stays blocked. The two allowed reads are what the rendered item and category pages fetch; blocking them made Google render item pages as **Item not found** with the default title.
- `GET /sitemap.xml` — dynamic sitemap (static routes + all items as `/{tag}/{slug}` with `lastmod` from `createdAt`); `Cache-Control: public, max-age=3600`.
- `GET /assets/fonts/*` from `src/assets/fonts/`.
- `GET /assets/brand/*` from `src/assets/brand/` (Apathy is Boring header logo, FES logo, both also in the site footer).
- `GET /assets/inventory/*` from `src/assets/inventory/` (seed images and `items.json`).
- **Caching rule:** these three mounts keep stable file names, so they are served with `Cache-Control: public, max-age=604800` (7 days). To change a font, brand image or seed photo, **add it under a new file name** and update the references; overwriting a file in place leaves returning visitors on the old copy for up to a week. Vite-built assets need nothing: their names change with their content.

### Data

- Inventory and reservations persist in **Supabase Postgres** via `src/lib/inventory-store.js` (service role key on the server). Apply `supabase/migrations/001_inventory.sql`, `002_reservation_approval.sql`, `003_lock_down_roles.sql`, `004_inventory_slug.sql`, `005_expertise.sql`, `006_consultation_scheduling.sql`, `007_expertise_copy.sql`, and `008_consultation_follow_up.sql` before first run (or after deploy if upgrading).
- Tables: `inventory_items` (`id`, `title`, `body`, `image`, `tag`, `slug`, `created_at`, `expert_email`, `long_body`) and `reservations` (`id`, `item_id`, `start_date`, `end_date`, `status`, `user_email`, `time_slots`, `request_summary`, `meeting_at`, `zoom_meeting_id`, `zoom_join_url`, `zoom_password`, `cancelled_at`, `cancelled_by`, `follow_up_of`). Unique index on `(tag, slug)`. RLS is enabled with no public policies — Express uses the service role (bypasses RLS). Migration `003_lock_down_roles.sql` revokes direct table access from `anon`/`authenticated`. Slugs are generated server-side at create/seed time from title (`src/lib/slug.js`); immutable after create; collisions within a tag append `-2`, `-3`, etc. `ensureInventory()` runs a once-per-process slug backfill (`ensureSlugsBackfilled()`) that is **decoupled from the `inventorySeeded` flag** — it always populates missing slugs on existing rows even when the inventory is already seeded, and retries on the next request if it fails (errors are logged, not swallowed, and never break the inventory read). `npm run backfill:slugs` triggers the same backfill on demand.
- **Public** API item shape (`GET /api/inventory`, `GET /api/inventory/by-slug/:tag/:slug`): `{ id, title, body, image, createdAt, tag, slug, longBody, reservations }` where `reservations` is `{ id, startDate, endDate, status }[]` — **`userEmail`, `expertEmail`, `timeSlots`, `requestSummary`, and `meetingAt` are never returned on public routes**. `body` is the description (expertise: short list text). `longBody` is the expertise bio, or `null` on other tags. `image` is a `/media/items/{id}/{hash}.{ext}` URL for uploaded photos or the seed `/assets/inventory/...` path, never a data URL. Admin route `GET /api/admin/inventory` returns full items including `userEmail` + consultation fields on reservations and `expertEmail` on items (same `image` mapping).
- `status` on reservations: `pending` (new member request), `reserved` (admin-approved, or consultation scheduled), `refused` (admin declined — dates freed), `cancelled` (consultation cancelled by member/expert/admin, or an equipment/book/room reservation the member withdrew or cancelled from `/account`, `cancelled_by: 'member'`), or legacy `available`. Admin deletes of equipment/book/room reservations are still hard deletes. New creates always use `pending` with member email from JWT.
- `pending` and `reserved` block calendar dates; only `reserved` marks the card **Unavailable** badge.
- **Tag-specific reservation rules** (enforced in `ItemCalendar` and `POST`/`PATCH` reservation APIs via `src/lib/reservation-rules.js`; ranges are inclusive):
  - **equipment** — Start must be a **Tuesday**; end is automatically the **following Tuesday** (+7 days). One-week block; pickup/drop-off hours message shown on the calendar.
  - **books** — Start must be a **Tuesday**; end is **four weeks later** (+28 days, also a Tuesday). One-month block; same pickup/drop-off message.
  - **rooms** — Flexible inclusive range on any days (existing two-click range selection).
  - **expertise** — No calendar. Consultation requests store the submission date as both start and end; free-text `time_slots` (max 500 chars) and `request_summary` (max 2000 chars) are required instead. Date collisions never apply (multiple members can request the same expert). Admin approval requires `meetingAt` (ISO timestamp, stored in `meeting_at`).
- Calendar UI for equipment/books: only Tuesdays are selectable; clicking a Tuesday selects the full fixed block. Equipment and books modals show localized pickup/drop-off hours (10am–5pm Tuesdays).
- **Stored** `image` (`inventory_items.image`) is either a data URL from the client compressor (WebP preferred, JPEG fallback; the server also accepts PNG and GIF) or a path like `/assets/inventory/images/...` for seeded MyTurn items. Write paths (`POST`/`PATCH /api/inventory`, `POST`/`PATCH /api/account/mentor-profile`) reject a data URL over 2,000,000 characters with **413** `{ error, code: 'image_too_large' }` and any other format or path (including SVG) with **400** `{ error, code: 'image_invalid' }`. Only the admin routes accept a seed path, and only a short plain one (at most 200 characters, `[A-Za-z0-9._-]` segments, no `..`); the member routes accept uploaded data URLs only. A `/media/items/...` URL is never stored: on the two `PATCH` routes, that item's own `/media/items/{sameId}/...` URL (any hash) means "photo unchanged"; elsewhere it is `image_invalid`.
- **Sent** `image`: every response that carries an item maps a stored data URL to `/media/items/{id}/{hash}.{ext}` (`hash` = first 16 hex of SHA-256 of the stored data URL; `ext` from the MIME: `jpg`, `png`, `webp`, `gif`), so a new photo gets a new URL and the old one redirects. The SSR head uses the same URL, made absolute, for og:image, twitter:image and the Product JSON-LD `image`. Storage is unchanged (no migration); `/api/inventory` drops from about 1.1 MB to about 11 KB of JSON with the current catalogue.
- Seeding runs via `ensureInventory()` in `inventory-store.js` (no-op after first successful seed via `inventorySeeded` flag). If the DB is empty: import `data/inventory.json` when present, else insert 9 seed items from `src/assets/inventory/items.json`.
- Every reservation/item write (`addReservation`, `approveReservation`, `scheduleConsultation`, `cancelConsultation`, `cancelReservationForMember`, `refuseReservation`, `removeReservation`, `patchReservation`, `updateExpertiseItem`, `deleteInventoryItem`) runs inside an in-process per-item lock (`withItemLock`) around read + write (single Cloud Run instance only; not safe across replicas). A refuse/delete that arrives during a schedule's Zoom call waits for it to finish.
- Seeded item IDs use the format `myturn-{sourceId}` when `sourceId` is present in the seed file.
- One-time upsert from legacy JSON: `npm run migrate:inventory` (or rely on auto-import when the DB is empty on first `GET /api/inventory`).

### Email (Resend)

- `RESEND_API_KEY` is lazy-initialized: the server starts without it (logs a warning); member approval/refusal emails fail with a clear error when sent if unset.
- Every app email (reservation decisions, welcome, contact form, consultation request / scheduled / cancelled) is rendered by `renderBrandedEmail()` in `src/lib/email-brand.js`: full HTML document plus a plain-text part. The English light wordmark is attached inline (`cid:aisb-logo`) so it does not depend on a deployed image URL. Layout: Mint header, uppercase Inter headline, Lemon button with Dark text, Grape links, dotted divider, Dark identification footer. No unsubscribe link (these are transactional). Copy stays English-only.
- **Routes wait for their emails before responding** (`settleNotifications()` in `server.js`), because Cloud Run can throttle CPU once a response is out and stall sends still in flight. A failed email (Resend error, missing key, or the 10 s cap `EMAIL_SEND_TIMEOUT_MS`) is logged and never turns a saved action into an error: approve, refuse, reservation create (expertise), schedule, cancel and the admin deletes that cancel consultations or upcoming member reservations add `emailSent: true|false` to their JSON. `true` means there was at least one email and Resend accepted all of them. A Resend 429 (`rate_limit_exceeded`; default limit 2 requests per second) is retried once after 1 s (`EMAIL_RATE_LIMIT_RETRY_MS`); nothing else is retried. Admin item deletes notify in paced rounds (`settleNotificationRounds()`, at least `EMAIL_PACING_MS_PER_EMAIL` = 0.5 s per email per round). The client reads `emailSent` only to drop an "emailed" claim: `AdminPanel` (approve, refuse, deletes, follow-up) and `AccountConsultations` (schedule, cancel, follow-up) show Kimchi's `_plain` bubbles when it is `false` (the cancel also checks `otherPartyEmailed`), and their hidden status lines add an "emailed" note only when it isn't `false` (`AdminPanel`: only when it is `true`); there is no warning UI.
- **Reply-To:** every app email except the contact form sets `replyTo: EMAIL_REPLY_TO` (default `CONTACT_TO`, `samuel@apathyisboring.com`). `activistresourcelibrary.com` has no MX record, so replies to `noreply@` would otherwise be lost.
- New pending reservation requests on equipment/books/rooms do **not** send email — admins are notified via the Slack webhook only. **Expertise consultation requests** send the member a "consultation request received" email and the expert (item `expert_email`, when set) a "new consultation request" email on submit.
- Member approval/refusal emails go to the reservation `userEmail` (from JWT at create time; skipped with log if missing). No env-based `EMAIL_TO` fallback. Expertise approvals schedule the consultation and send the scheduled emails (Zoom link + `.ics`) to member and expert. The member message includes "This project is funded by YES Employment." and the data-sharing form link (**placeholder `CONSULTATION_DATA_FORM_URL` in `server.js` — replace before launch**). A funder logo strip renders above the footer only when `EMAIL_FUNDER_LOGO_URL` is set.
- Member welcome email on sign-up: `POST /api/auth/welcome-email` (client fire-and-forget after sign-up or first sign-in within 7 days); links to `/howthisworks` and `/about`; deduped via `user_metadata.welcome_email_sent`.
- About-page contact form emails go to `samuel@apathyisboring.com` with `replyTo` set to the submitter's email (`POST /api/contact`; requires `RESEND_API_KEY` at send time).
- Equipment and book approval emails include the Tuesday pickup/drop-off hours and the office address from `orgContact` (default `5310 Boulevard Saint-Laurent, Montréal QC H2T 1S1`) and close with "We look forward to seeing you at pickup." Room approvals have no pickup notice: they confirm the dates and the office address (**Where** row) and close with "If anything changes, just reply to this email." Reservation emails write dates out in English (`formatReservationDates()`).
- Admin deletes of an equipment, book or room reservation (or of its item) email each member whose reservation was `pending`, or `reserved` and not yet over: "Your reservation for {item} ({dates}) was cancelled by the Activist Resource Library team", with a link to the category page (`buildReservationCancelledByTeamEmailPayload`). A member withdrawing or cancelling their own reservation from `/account` gets no email.
- All Resend email links use `SITE_URL` (or `VITE_SITE_URL`), falling back to `https://activistresourcelibrary.com` when unset — member decision emails link to the item and library home. The header logo is an inline attachment, not a site URL.
- `EMAIL_FROM` defaults to `noreply@activistresourcelibrary.com`; legacy `onboarding@resend.dev` in env is ignored at runtime.
- Footer contact (`orgContact` in `email-brand.js`): Apathy is Boring · address · phone · apathyisboring.com. Optional env overrides: `ORG_ADDRESS`, `ORG_PHONE`. `npm run cloud:build` passes `ORG_PHONE` when set; it does not pass `ORG_ADDRESS` (the comma breaks gcloud's env list).

### Server port

- Default `PORT=3000`.
- In development (`NODE_ENV=development` or `STRICT_PORT=true`), the server exits if the port is already in use so the Vite proxy target stays correct. `npm run dev` pre-clears the port automatically; `npm run dev:server` does not.
- Outside development, if the port is in use, the server tries successive ports (up to 20 attempts).

## Docker / Cloud Run

Production image: multi-stage `Dockerfile` at the repo root.

| Stage | Role |
|-------|------|
| `build` | `npm ci` + `npm run build` (Vite → `dist/`; copies `locales/` + `content/contracts/` for i18n and member agreement imports) |
| `production` | `npm ci --omit=dev`, `node server.js` (copies `src/lib/` for shared server helpers, `src/assets/` for fonts, brand logos, seed images, and the inline email wordmark, and `locales/` for server-side SEO copy) |

**Build-time args** (optional fallback — client auth primarily uses runtime `/config.js`):

- `SUPABASE_URL` / `VITE_SUPABASE_URL`
- `SUPABASE_API` / `VITE_SUPABASE_ANON_KEY`
- `SITE_URL` / `VITE_SITE_URL` — production origin for Supabase email-confirmation redirects (recommended for Cloud Run deploys)

**Runtime env** (Cloud Run / container platform):

- `SUPABASE_URL`, `SUPABASE_API` (required — client auth via `/config.js` + inventory storage)
- `SUPABASE_SERVICE_ROLE_KEY` (required — inventory storage; **Cloud Run deploy via `npm run cloud:build` mounts from Secret Manager**, not plain env vars)
- `SITE_URL` (recommended — email confirmation redirects)
- `RESEND_API_KEY` (required for member approval/refusal emails; **Secret Manager on Cloud Run** when set in `.env` during deploy)
- `PORT` (Cloud Run sets this automatically, default `3000` locally)
- `EMAIL_FROM` (optional)
- `EMAIL_REPLY_TO` (optional; passed by `npm run cloud:build` when set in `.env`)
- `ZOOM_ACCOUNT_ID`, `ZOOM_CLIENT_ID` (plain env) + `ZOOM_CLIENT_SECRET` (**Secret Manager** `zoom-client-secret`) — set by `npm run cloud:build` when present in `.env`

**Secret Manager (Cloud Run):** Before first `npm run cloud:build` deploy with secrets, create `supabase-service-role-key` and optionally `resend-api-key` secrets and grant the Cloud Run service account `secretAccessor`. One-time `gcloud` commands are documented in the comment block at the top of `scripts/cloud-build.sh`.

**Local build and run:** `npm run docker:build` reads Supabase vars from `.env` and passes them as Docker build args. Override the tag with `IMAGE=region-docker.pkg.dev/project/repo/arl-online:latest npm run docker:build`.

```bash
docker build \
 --build-arg SUPABASE_URL=https://your-project.supabase.co \
 --build-arg SUPABASE_API=your-anon-key \
 --build-arg SITE_URL=https://activistresourcelibrary.com \
 -t arl-online .

docker run --rm -p 8080:8080 \
  -e PORT=8080 \
  -e SUPABASE_URL=https://your-project.supabase.co \
  -e SUPABASE_API=your-anon-key \
  -e SUPABASE_SERVICE_ROLE_KEY=your-service-role-key \
  -e RESEND_API_KEY=re_xxxx \
  arl-online
```

**Cloud Run:** choose **Dockerfile** as the build type; pass build args for Supabase if auth is enabled (or rely on runtime `/config.js`); map runtime env for `SUPABASE_URL`, `SUPABASE_API`, email vars; mount `SUPABASE_SERVICE_ROLE_KEY` and `RESEND_API_KEY` via Secret Manager (see `scripts/cloud-build.sh`).

**www host:** `www.activistresourcelibrary.com` needs its own Cloud Run domain mapping (service `arl-online`, region `us-east1`) and the DNS record Google shows for it (normally `CNAME www → ghs.googlehosted.com.` at Namecheap) so Google issues a certificate. The apex sends HSTS with `includeSubDomains`, so a plain-HTTP DNS redirect would not work for returning visitors. Once requests reach the service, `server.js` 301s them to the apex (sessions, OAuth redirect URLs and canonical URLs all use the apex).

**Persistence:** Inventory and reservations live in Supabase Postgres. Apply `supabase/migrations/001_inventory.sql`, `002_reservation_approval.sql`, `003_lock_down_roles.sql`, `004_inventory_slug.sql`, `005_expertise.sql`, `006_consultation_scheduling.sql`, `007_expertise_copy.sql`, and `008_consultation_follow_up.sql` to your project before deploying.

## Google Search Console setup

1. **Verify ownership** — In [Google Search Console](https://search.google.com/search-console), add the property `https://activistresourcelibrary.com` (URL-prefix or domain property).
2. **HTML tag or DNS** — Use the meta-tag verification method (temporary tag in `index.html`) or DNS TXT record via your domain host. Remove the verification meta tag after confirming if you used the HTML method.
3. **Submit sitemap** — After deploy, submit `https://activistresourcelibrary.com/sitemap.xml` under **Sitemaps**. The dynamic sitemap lists static routes plus every inventory item at `/{tag}/{slug}` with `lastmod`.
4. **Check robots.txt** — Confirm `https://activistresourcelibrary.com/robots.txt` allows `/`, `/api/inventory$` and `/api/inventory/by-slug/`, disallows `/api/`, `/admin` and `/account`, and references the sitemap URL. Re-fetch it under **Settings → robots.txt** after a deploy that changes it.
5. **Inspect URLs** — Use **URL inspection** on the homepage and `/howthisworks` to confirm canonical, hreflang (`?lang=en` / `?lang=fr`), and Organization JSON-LD on public pages. On an item page (e.g. a `/books/...` URL from the sitemap), **Test live URL → View tested page** should show the item title in the screenshot and HTML, and **More info → Page resources** should list `/api/inventory/by-slug/...` as loaded, not blocked; the item page should carry exactly one Product and one Organization JSON-LD block. `/admin` should show `noindex` (meta + `X-Robots-Tag`). A made-up path (e.g. `/how-it-works`) or a deleted item's URL should return **404** (Not found), not Soft 404.
6. **Optional analytics** — Set `PLAUSIBLE_DOMAIN=activistresourcelibrary.com` in production env for privacy-friendly traffic data alongside Search Console.
